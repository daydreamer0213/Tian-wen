# 独立案例的来源输入边界核对（2026-09-30）

## 本轮决定

不直接把案例设计输入改成“任务类型＋失败类别”，也不把删除部分来源字段当作独立性修复。前者丢失已修复的原始反馈边界，后者仍可能通过反馈原话、目标或标准携带来源事实。本轮没有修改生产代码、模型提示、研究门槛或日常安装。

这是对 E104/E106 遗留问题的设计可行性核对，不是新的真实模型实验或学习效果证明。完整自动学习仍未通过；已有 024 预览产品交付不重新验收。固定决策窗口及原停止条件不变。

## 已有保护能证明什么

E106 的文本保护比较来源直接请求（不带先前上下文）和此前生成的案例请求：规范化后存在一个共享的 20 字符窗口，且窗口内含至少两组数字时会被拒绝。较长共享片段里的两组数字若不能同时落进一个这样的窗口，也不会因此命中。它能拦住已记录的明显数量事实照搬，不能证明换词、重排、单项事实复用或经反馈／上下文进入的新案例在语义上独立。其他摘要去重也不能补成这个证明。文件案例不能据此宣称有同样的文本数量检查。

另一方面，R9 已暴露派生标准把“助手自己的建议”变成“用户自己的建议”。[职责复核](tianwen-responsibility-and-acceptance-scope-review-20260908.md)明确保留三个消费者的完整原话传递，不允许再只靠解释后的标准判断主体、否定和例外。这个既有修复不能为了减少案例设计输入而撤回。

本轮仅运行已有 `natural correction recovery` 六个变体，结果 **6 通过、92 跳过，总计 98**，退出码 0。有效材料变体验证案例设计、候选提议及试验审查的原话恢复；缺失或篡改变体验证停止保护。这是脚本式工程测试，测试中的激活不代表 Daily 激活，不证明真实模型理解正确或新案例事实独立。没有运行整组、构建或新模型调用。

日志与源码／测试日志哈希收据分别为 `D:/DevData/tianwen-case-input-review-20260930/feedback-boundary-tests.log` 和同目录 `investigation-receipt.json`，合计 1,829 字节。独立只读复核指出旧拦截器必须准确描述为 20 字符窗口，已修正；材料表及补完的拆分取舍复核未发现其他可操作问题。复核未运行测试或模型，也不证明其他拆分方案不可行。

## 方案取舍

| 方案 | 可以得到的改善 | 当前决定 |
| --- | --- | --- |
| 维持现有来源材料、明确 E106 的窄保护范围 | 保留原话及来源恢复，承认语义独立尚无保证 | 当前行为维持；不是完整问题已解决 |
| 仅传任务类型与失败类别 | 降低来源事实的显式暴露 | 不采用：类别不足以表达真实反馈要求，也撤掉案例设计收到原话的既有边界 |
| 删原始请求／上下文，保留目标、标准和反馈原话 | 减少一部分材料 | 不作为修复实施：余下字段仍可携带事实或未解指代，也没有一般性依据确定被删上下文无用 |
| 将“理解真实反馈要求”和“生成全新事实”拆开 | 有机会降低事实复用，同时保留负责解释反馈的消费者 | 可研究的设计方向，尚未证明可行；中间说明本身可能漏事实或解释错，不应仅换字段名就宣称独立 |

## 拆分方向的有界可行性比较

现有分工不能只靠重组字段就完成这项拆分：

1. 复用现有反馈评估的 `supplementalCriteria` 和范围核对结果，事实生成者仍只收到派生解释，不再收到原话。这正是 R9 修复前的缺口；范围核对证明也不是无来源事实的完整任务说明。
2. 让现有案例设计者在同一次调用中先写说明、再生成事实，没有减少同一个模型看到的来源材料，不能把两个输出字段当成两个隔离角色。
3. 再增加一次说明转交／事实生成调用，才可能形成显式输入分工，但新增说明的主体准确性、未解指代和事实泄漏没有现成依据。它是新的架构方案，而非这次可直接实施的窄修复；不能以“说明里没有事实”的模型声明代替验证。
4. 由宿主直接生成固定题目模板可以让事实不取自来源，但现有产品支持不同任务族和文件任务，没有与所有反馈要求匹配的通用模板。为眼前摘要样本加专用模板会缩窄产品范围，不能当成一般解决方案。

**本轮收口：未找到同时保持既有原话职责、减少来源事实暴露且可直接落地的窄改动，不开启新的案例盲化实现或模型角色扩张。**这不是证明今后任何设计都不可能；只是上述最直接方案的取舍已明确。现有来源输入维持，E106 局限和自动学习未通过照实保留。后续以实际项目工作及其自然反馈推进，不把本调查再变成一串待验的摘要／生成轮次。
