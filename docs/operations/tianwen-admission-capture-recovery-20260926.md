## 028 失败与接口边界

028 的 S2 准入子会话输出了符合新包裹结构的普通文本 JSON，但没有调用 `structured_output`。原生子代理的 `outputSchema` 只校验实际提交；安装的 DSH 接口没有可用的“必须调用这个工具”参数。把文本 JSON 直接当判断会丢失原生提交证明，因此继续拒绝这种结果。

本候选只在**任务准入**子会话中处理这类遗漏：如果第一步结束前完全没有工具调用，主机在同一个原生会话内发送一次固定提醒，要求通过 `structured_output` 提交。它不会解析或采纳第一段文本，不新开任务，也不重试独立任务复核。第二步仍不提交时，准入保持 `invalid-judgment`，不生成证明。已有工具调用后的模式校验失败继续由原生工具处理，不额外提醒。

恢复证明同时检查原请求、第一段无工具回答、唯一且固定的提醒、后续成功的原生工具调用和会话摘要。普通评审的证明恢复不允许该提醒；旧扁平准入证明继续按旧值核验。工程测试覆盖“先文本后工具”“提醒后仍无工具”以及旧证明兼容。提醒增加一次模型请求的可能性，**提高可恢复机会但不保证真实模型一定提交**。

验证：准入、观察、反馈、引导循环与账本五个相关测试文件共 221 项通过；八个 TypeScript 包的类型构建通过，差异空白检查通过。测试期间发现一项历史引导测试仍提交旧扁平准入结构，已改为当前包裹结构并单独复测。以上均为脚本模型和工程证明，未计作真实 DeepSeek 验收。

## 读取边界与下一轮

028 的主任务回答读取了同一验收根目录下的协议和请求文件，这是另一个独立问题，并非准入未调用工具的原因。当前 Windows `Workspace Write` 限制写入，不能证明工作区外读取被隔离；不得把它描述成完整盲测边界。本工程候选不擅自限制普通产品任务的读取能力。

下一轮若做有限真实验收，使用新的源码身份、Profile、工作区、账本和新任务；协议、题目清单与审计文件不放在模型工作区或其父目录/兄弟目录的可发现位置。输入前冻结材料和判定规则；任务各发一次，不重抽失败样本。逐项检查原生工具调用中的文件读取路径，发现验收材料泄露即将该任务判为污染。只有准入、反馈、研究实际输入、提案消费、方法采用与后续使用各自有原生证据时，才分别报告对应进展；工程测试通过不能代替这些结果。
