## 结论与当前动作

天问负责从任务中收集证据、判断问题归属、评估有限改进并治理未来使用，
不负责保证每个任务或每次模型判断都正确。验收要检查前者，不能无限追加后者的专项规则。

- 撤下尚未实施的“独立反馈分类＋草稿承诺 v7”组合修复计划。
  不因这份旧计划升级 Runtime022/Desktoppreview23，也不启动其 R11 文案诊断。
- 保留已经完成的用户原话传递修复和现有 v6 版本边界；本次不回滚源码，
  也不把既有评估规则悄悄放宽成自动发布。
- 当前最高价值的缺口是：原话传递修复虽有工程验证，但 R10 未进入方法试验，
  因而其三个学习消费者尚缺本版真实模型运行中的完整证据。
- 所有首次失败、原始评分、独立检查及 R9/R10 首次不发布决定保留。
  本复核改变后续工作归类，不重新评分旧答案，也不追认本版发布。

## 职责分界

| 观察到的情况 | 首要归属 | 天问应负责到哪里 |
| --- | --- | --- |
| 文案不够好、代码没写对、某个任务的答案出错 | 执行模型、工具或具体 Skill/任务 | 可记录为学习材料；先判断归因和可复用性，不直接把案例规则写进核心 |
| 用户反馈没有进入识别、关联错对象、原话在下游丢失或被解释替代 | 天问反馈和证据链 | 核实输入、原文、关联、消费者及持久记录；区别模型误判与宿主丢失 |
| 评估模型对答案判断有误 | 评估可靠性观察 | 保留分歧及影响；不能仅凭分歧要求无限调提示词，也不能宣称评估必然准确 |
| 丢失证据仍晋升、把错误归因当作改进、越作用域影响后续任务、旧运行被改写 | 天问学习与版本治理 | 属于产品问题；追踪实际决策、依据和后续影响，不能用“模型会犯错”免责 |
| 没有可支持的重复问题、候选被拒绝、试验结果不确定 | 正常学习结果或证据不足 | 不强行生成候选，不为触发而降低门槛；明确哪些路径没有验证 |
| 验收启动器或独立诊断环境配置错误 | 验收工具/环境 | 修验收环境，不误记成产品故障；保留首次错误 |

上述边界依据架构总览第 3、5、8 节，尤其是 Learning Intake/Attribution
对问题归属的判断、允许 no Case/no Lesson/no Candidate，以及失败语义分离。
自然对话设计另明确：持续偏好可以成为依据，不必先证明旧答案客观错误；
记录反馈不等于必须学习，学习也不等于必须采用。

## 逐项重归类

### 1. R9 原话缺失于下游：保留为主线产品修复

R9 的原始反馈指向“助手自己的建议”，派生标准却变成“用户自己的建议”。
案例设计、候选生成、来源任务评估只收到派生标准，候选也沿用了错误主体。
这是实际学习链上的归因/材料缺口，不只是原任务文案不好。

本版已让三个消费者收到绑定到来源的完整 `originalFeedback`，并将它与
答案的事实依据、盲测执行者输入分开。工程测试和原生持久化恢复检查已完成。
但 R10 没有方法试验，不能把这一版的真实消费者覆盖填成通过。
下一验证只回答原话是否真实到达、是否保持主体/范围、是否按既有规则得出学习决定。
不以试验必须接受、候选必须改善所有答案为目标。

### 2. R10 U4 空反馈：保留识别局限，不认定分类代码挡路

U4 的完整原文、前文和对应任务 ID 均在原生输入中；模型输出了
`kind: conversation`、空反馈和空关联。宿主如实保存，没有丢失返回字段。

代码并不按 `conversation` 排除反馈：

- `conversation-observer.ts` 的说明允许 feedback-only conversation；反馈状态独立看 `feedback`。
- `conversation-feedback-assessment.ts` 的后续消息筛选看任务关联和非空反馈，不看后续消息的 `kind`。
- `conversation-feedback.spec.ts` 和 `conversation-guidance-loop.spec.ts` 已覆盖纯反馈对话进入评估及学习路径。

所以“聊天标签导致漏反馈”不是已经证明的根因。把两个决定写得更明确至多是
一个可选改进假设，不能仅凭共现强制再开一轮提示词修复或重复既有测试。
这次漏识别仍是自然使用中的真实局限；没有被抹掉，也不代表全部触发路径不可达。

### 3. R10 草稿承诺与原生 met：记录质量风险，不添加专项核心规则

独立检查发现 U1/U2/U3/U6 的草稿质量问题，原生评估给出 met；U2 的明确限制
和答案也确实同时在两个评估输入中。分歧是真实的，不改写成答案合格。

但这不是缺少材料、绑定错误或旧版本误用。R10 没有试验、没有采用新方法，
不能称其已经传播了错误学习。专项“真人草稿/礼貌承诺”v7 修复撤出本轮主线。
不因此增加第三评委、词句过滤、写作禁令或新的质量版本。

评估可靠性仍影响产品可信度：若有证据表明错误判断让具体错误改进实际通过并影响
未来任务，应检查那条学习决策链及其归因，不能泛称一切都属于执行模型。
也不能把“另一个 AI 不同意”自动当作通用最终真值；需保留原任务标准及可核实依据。

### 4. 无试验、等待、诊断环境：分别处理

- R10 最终 1 条反馈、0 个试验、0 次采用。未满足两条支持来源时没有试验，
  是当前台账下的正确选择；这既不证明识别完整，也不证明未达路径通过。
- 两次偏好输入约 56 秒、47 秒才出现首段普通文本，是真实体验局限。
  本轮没有调度修复，也没有已约定的响应时限可据此宣称通过或违约。
- 六例独立语义诊断因自身注入声明遗漏而失败，正常产品服务声明完整。
  旧诊断保留；既然专项写作修复撤出，不为完成这套诊断而另造新一轮环境。

## 后续验收与结束条件

验收分开报告四项，不合并成一个“全部成功”：

1. **正常使用：** 无斜杠、材料包或手动反思指令，原生 DSH 完成实际模型调用；
   卡点、错误、等待照实记录。已经获得的 R9/R10 证据不因范围纠正作废。
2. **学习机制：** 对具有明确来源的反馈，原话、归因、候选输入与持久凭据一致；
   决策遵守现有同意、支持来源、独立评估、版本和回滚约束。不强求采用。
3. **任务效果：** 答案好坏、评估分歧及候选是否真的改善另列结果。
   有限样本不是长期进化证明，机制正确也不是“永不学错”的保证。
4. **交付：** 当前改动的必要证据齐备且作出明确发布判断后，才执行既有
   合并、准确主线版本 CI、备份、日常安装与旧数据保护检查。

具体下一步是复用现有测试与原生接缝，准备一个范围受限的、当前修复版的
真实反馈链验证。普通输入和反馈由浏览器送入，模型答案与学习决定未知；
只核查既有三个消费者及治理结果，不混入被撤下的草稿专项诊断。
在调用前固定目的、场景和判断依据；未触发则保留未触发及实际原因，不补发
近似输入追求通过。受控工程分支测试与普通真实模型使用仍分别标注。

在上述缺口核实前不声明本版已发布。当前源码和日常安装不因本次文档纠偏改变。
不要求用户逐项批准普通测试细节；重大目标、权限或产品责任变化仍须单独决定。
