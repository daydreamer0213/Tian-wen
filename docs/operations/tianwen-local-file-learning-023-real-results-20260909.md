## 最早失败点与职责

F1同一条原生assistant消息（seq1504）同时提出glob与pwsh。glob先执行
（1505–1506），成功返回两份原件名称；pwsh随后也成功列目录。因此不能说是
“搜索失败才退回PowerShell”。当前 `conversation-file-observer.ts` 只接受
read/write/edit，第一个glob就记录unsupported-tool，后续不再捕获原始文件。
F1随后还使用pwsh和skill；C1同样使用glob/pwsh，后续另有grep。

这是普通使用与当前取证合同不匹配：文件任务正常完成，自动识别也正确，但正常
发现文件的步骤即取消证据链。它不是总结措辞或某个子任务没做好。不能把工程检查
中只使用三种工具的成功，扩大成标准DSH工具组合已经可用。

原生接口的只读核对发现：

- 固定内置glob/grep通过无Shell、固定参数的ripgrep执行，并使用`--no-config`；
  可能另写自有超量结果存储。可研究窄适配，但新内容与来源仍须绑定，不能仅放行名称。
- skill只从provider读取文本、不执行技能脚本；provider可插拔，须保留准确提供者
  与批准来源身份。本次F1真实读取summarization属于普通任务用技能，**不是新学习
  研究的来源选择或改编分支**。
- pwsh接收任意命令，展示说明由模型填写，不能作为“只读”证明。没有现成的可信
  `Get-ChildItem/pwd`命令分类器。原生沙箱实时结果虽有mode/enforcement，但
  当前Windows后端只声明partial，且这些result.value事实未原样持久化到Session。
  不能事后仅凭命令文本或文件前后相同，补造完整的不修改证明。

只放行glob仍不能修复这两次实际轨迹，不能修改旧分类/收据或重问同题刷绿。
