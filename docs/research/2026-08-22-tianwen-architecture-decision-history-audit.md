# Tianwen 架构问答决策历史审计

日期：2026-08-22

状态：历史决策证据，不是当前产品事实的首要权威。

来源：

- 架构任务 `01a00d5a-8974-7c41-b660-127c15fcecb6`；
- 架构监督任务 `01a01987-c79b-7891-ac33-ec81404d61d1`。

当前事实发生冲突时，仍按“当前代码与 exact-SHA 证据 → canonical 文档与运营 handoff → 本审计 → 旧中间判断”的顺序处理。

## 1. 审计方法与覆盖范围

两份任务共 309 个 turn：

- 114 个只有实施任务交接，没有新的项目所有者问答；
- 44 个是 `ok`、继续、批准等例行确认；
- 151 个包含实质性问答、状态追问、方向纠偏或授权说明。

151 个实质问答全部逐条分类。只有满足以下至少一项，才提升为本审计的决策案例：

1. 项目所有者的介入改变了产品方向、组件归属或阶段边界；
2. 项目所有者指出方案奇怪、过重、过轻、反复或与主流做法不符；
3. 回答形成了后来继续使用的架构原则、默认策略或监督协议；
4. 后续代码、CI 或真实运行对该决定给出了正面或反面证据；
5. 即使换成另一个问题，该推理方法仍然有用。

每个入选案例至少还原：具体问题、项目所有者原话、回答形成的最终方案、可迁移方法和适用边界；后续代码或运行证据确实影响结论时一并记录。状态询问、一次性权限恢复、旧预算数字和临时网络故障已审阅，但不冒充架构经验。

### 1.1 对旧提炼结果的反向审计

这次审计不仅找遗漏，也把已经写入设计和个人监督 Skill 的条目重新对回完整问答。发现并纠正了以下压缩偏差：

| 旧提炼 | 为什么不准确 | 校正后的通用方法 | 处理 |
|---|---|---|---|
| “不破坏普通 Agent 的观察—行动—反馈—修正—收尾循环” | 把验收现象写成了根因，容易让人误以为 Tianwen 需要长期维护一套“循环兼容”原则 | 普通能力先查主流和上游归属；能复用就复用，只有已证明的产品差异才自建。完整循环只检查薄适配没有扭曲上游行为 | 已改写设计与个人 Skill |
| “结合项目设计”和“用户负责方向”合成一条沟通规则 | 混淆了两个独立问题：谁拥有决定，以及方案应从什么语义起点推导 | 先从 canonical 产品不变量和业务流程推导，再映射接口；用户—监督分工另行处理 | 已拆为独立案例 |
| “同类问题跨两轮就上移抽象层” | 把一次历史过程的轮次写成通用阈值，形成新的机械规则 | 补丁持续换形、只能解释最新症状或真实连接仍断开时，基于根因证据重新找协议所有者；不机械数轮次 | 已删除固定阈值 |
| “用户偏好通俗汇报” | 只记成写作风格，会漏掉用户介入通常是在提示方向偏移、方案不合理或隐藏约束未暴露 | 用户纠正先作为 architecture-fitness 信号调查；面向用户用故事和取舍汇报，收敛后再转成可执行文档 | 已提升为监督方法 |
| “真实 / 模拟”二分 | 会把真实 Runtime 上的受控评价误当自然用户证据，或因没有外部用户让项目停摆 | 分别记录任务来源、执行路径、评价者和可推广范围，按证据实际支持的最强结论命名 | 已改为四级证据和多维来源 |

反向审计没有发现会推翻当前 v0.1 路线的矛盾；它改变的是推理方法和表述精度，而不是恢复旧产品路线。

## 2. 可迁移的架构与监督方法

### 2.1 先从 canonical 产品语义推导，再映射当前接口

**来源。** `01a01987.../01a01ea5-63e9-78c3-89a0-9631b22a773c`、`01a01987.../01a01eac-2b9b-73d2-8e5c-f3b069cc77c6`。

**具体问题。** Stage 2 曾直接使用最顺手的 DSH Session、same-session Goal 和 `blocked` 状态，把“不同 Session 计数”和“只消费 blocked Goal”写成学习语义。这样容易实现，却压扁了 Tianwen Run、业务 Outcome、Observed Gap 和 Signal/Ticket。

**项目所有者原话。** “你给方案的时候我希望你结合项目已有的架构和设计文档去考虑……不要机械的给方案，要结合项目的设计。”随后强调：“记住要从项目的文档出发，不然文档不就白写了吗？”

**回答形成的方案。** 恢复 `Tianwen Run → Evidence → Outcome → Observed Gap → Signal/Ticket`；DSH Goal、Session、工具错误码和 verifier 都只是事实来源。产品缺少身份连接时补最薄 Run binding，不把 Session 改名成 Run，也不扩建 Goal Graph。

**可迁移方法。** 先定义产品不变量、业务流程和模块职责，再检查现有接口能否直接承载、需要薄适配还是暴露了真实缺口。接口说明“现在怎样实现”，不能自动决定“产品是什么”。

**边界。** canonical 文档也必须经过当前代码、Git、测试、CI 和真实运行校验；被后续证据推翻的文档应先更新，不能机械照搬。

### 2.2 普通能力先审计主流与上游归属

**来源。** `01a00d5a.../01a018ae-6973-7023-b69d-4957bf28db25`、`01a00d5a.../01a018d8-a941-7c33-9f1f-692d08d303d1`、`01a00d5a.../01a00ea4-83af-7300-9efa-1ba7b176d73d`。

**具体问题。** Python Alpha 逐渐自行承担 Agent Loop、工具、Session、恢复、预算和终止；开发不断修补实验执行器，没有先问这些组件是否本来就不该由 Tianwen 实现。上游 DSH 又在 rc.7 增加了 Jobs、Workflow 和 Feedback，使旧能力清单更容易误导归属判断。

**项目所有者原话。** “这部分问题，到底是写的时候没写好，还是本来就不需要写……有现成的能力优先复用，然后适应修改，最后手段才是自己手写。”

**回答形成的方案。** DSH 成为唯一 Runtime，普通 Agent 能力按“直接复用 → 配置或薄适配 → 只有 Tianwen 特有治理才自建”处理；Python Alpha 冻结为实验和验证资产。

**可迁移方法。** 组件归属审计必须基于当前主流方案和当前上游公共能力，不只看项目早先安装的版本。严格、确定、易测都不足以证明项目应拥有该组件。

**边界。** 上游存在类似名词不等于已经满足产品语义。Evidence、跨 Run 归因、Candidate、Evaluation、Promotion 和 Rollback 仍需按公共能力实际合同逐项判断。

### 2.3 把承重架构方案当作可证伪假设

**来源。** `01a00d5a.../01a0182e-fd74-7423-ba01-322b442fc056`、`01a00d5a.../01a0182b-15ed-7da2-b1d6-a82a53f74e8d`、`01a00d5a.../01a018bf-a89f-7330-a73e-4c27bc31bacd`。

**具体问题。** 合理目标被机械翻译为硬限制：控制成本变成 8/10 次请求断电，控制写权限变成缩小读取范围，保护检查输出变成不给 Agent 可操作反馈。TDD 和 correctness review 只能证明实现忠实于规则，无法证明规则值得存在。

**项目所有者原话。** “不是机械照搬规则，而是机械实现方案，但是没有对方案去分析过是否合理。”

**回答形成的方案。** 承重设计编码前先只描述问题，再调查主流做法、比较候选方案、说明 Tianwen 为什么需要不同、评估正常能力损失，并用最小实验验证。方案合理性审查在实现正确性审查之前。

**可迁移方法。** 规格不是天然正确。对影响终止、权限、工具反馈、Skill 加载、证据分类和晋升的规则，要同时问：它降低了什么风险，又损失了什么正常能力；什么证据能证伪它。

**边界。** 普通字段和局部辅助函数不需要完整架构实验；只对会改变核心行为或治理结论的承重方案使用。

### 2.4 用完整真实故事和反例检查架构关系

**来源。** `01a00d5a.../01a00ffd-9012-76b2-82fe-66de9db5453e`、`01a00d5a.../01a00ff4-6fc7-7151-99a0-94db43caaa1c`、`01a00d5a.../01a018b7-9688-75b3-82b8-62fd0731b5f2`。

**具体问题。** 早期总览把任务准备、DSH 执行、学习和晋升画成流水线，单个模块内部完整，但“视频留存率低”这样的真实业务结果找不到合理入口，Goal 循环和学习循环又像三套独立引擎。

**项目所有者原话。** “模块内部的结构感觉没什么问题，但是模块与模块之间的关系……有点混乱。”

**回答形成的方案。** 以完整故事重画：长期 Goal 产生 Task，标准 Agent 执行，Outcome 先回到 Goal 分诊，少量可复用问题进入学习旁路，经过验证的新版本只影响未来任务；DSH 是共享执行底座，不是流水线中的一个阶段。

**可迁移方法。** 评审架构图时不要只数模块。选择一个典型故事、一个不应触发该模块的反例和一个失败故事，逐步问每个事实从哪里来、由谁决定、流向哪里。真实例子放不进去通常说明关系层缺失，而不是字段不够。

**边界。** “看起来优雅”不是单独证据；清晰关系仍要由合同、代码和运行事实承重。

### 2.5 优先采用标准语义，并穿过真实生产者—消费者

**来源。** `01a00d5a.../01a01511-2ffd-7e73-9623-bbc3ca1bb34f`、`01a00d5a.../01a01514-94fd-75f3-9a4a-44a6571c6362`、`01a01987.../01a02523-d477-77f3-a683-c22a7ba5a01a`。

**具体问题。** Verifier 的正常 `print()` JSON 被消费者因 CRLF 拒绝，首个修法又发明“恰好一个 LF”。installer 机器 JSON 又在 pnpm/Windows shell 包装层反复受污染。

**项目所有者原话。** “正常解析器是怎么样的？容错率这么低的吗？”以及“要不你查查主流方案是怎么解决这类问题的？感觉反反复复修了好久。”

**回答形成的方案。** 使用 UTF-8、标准 JSON、schema 和业务语义分层校验；原始摘要独立用于审计。机器协议由实际 CLI 拥有，stdout 只放合同输出；Node 原生入口和原生 Windows CI 承重。测试从真实 producer bytes 走到真实 consumer 和 durable store。

**可迁移方法。** 低层格式、平台和传输问题先采用标准库与原生平台合同。当补丁不断换形、只能解释最新症状或真实连接仍断开时，上移一层重新找协议所有者；不要把历史修复轮次写成固定门槛。测试必须验证真实连接，不只是两端各自吃理想 fixture。

**边界。** 真正的流式 framing、签名或 NDJSON 可以规定精确字节；普通有界 JSON 文档不需要自创协议。

### 2.6 最小充分由“下一步能否判断”决定

**来源。** `01a01987.../01a023aa-c978-7b53-af14-d79fbd2c7114`、`01a00d5a.../01a017e8-10db-7021-b58a-173b4f4cc461`。

**具体问题。** 自然任务失败时，为隐私隐藏全部底层错误，只剩无法定位的通用失败；另一处真实试验又在第一次运行前冻结大量 B2/B3、参考实现和矩阵，最小跑道膨胀成“体育场”。

**项目所有者原话。** “我不是说强求建设越少越好，而是强调，设计要有必要性……不希望你从过度设计转向另一个懒惰设计的极端。”

**回答形成的方案。** safe failure 在源边界提供闭合、非敏感阶段码，足以决定下一检查点，但不建设日志平台。试验只保留空白项目、冻结任务、客观 verifier 和薄启动入口；其他设施等真实需要再建。

**可迁移方法。** 每项机制都要回答它解决哪个当前可达问题；每个被省略的信息也要回答省略后是否仍能做出安全决定。最小的是实现范围，不是信息充分性。

**边界。** 未知输出仍 fail closed；固定阶段码不足时，先只读调查或窄探针，不立即扩成通用诊断系统。

### 2.7 安全门同时计算风险成本和干扰成本

**来源。** `01a00d5a.../01a01317-31c6-7392-ba89-aff4152a82cb`、`01a00d5a.../01a00de6-2395-74f3-8d6f-c13882025cb4`、`01a01987.../01a021dd-4a55-75e2-be8a-f9055146d4d2`。

**具体问题。** 十分钟价格快照、每次真实运行 TTY 确认、低风险等级变化再询问和理论极端缺口，开始阻塞主线。

**项目所有者原话。** “关键不在于权限的变化，而在于权限的边界。”以及“概率根本很低甚至不会发生的设计完全没必要。”

**回答形成的方案。** 既有 Goal、资源、影响和累计预算范围内自动推进；风险等级决定日志、试运行范围和回滚，授权边界决定是否询问用户。只让正常路径真实可达、会破坏核心承诺的问题阻塞。

**可迁移方法。** 安全设计同时评估事件概率与损失、保护措施造成的中断与失败概率。审计不等于审批，风险标签不等于弹窗。

**边界。** 越权、超预算、凭据、不可逆数据损失、外部发布和 Promotion 仍是明确门禁；候选不能修改自己的授权边界。

### 2.8 先写证据最强能支持的结论

**来源。** `01a01987.../01a0293f-8ae7-7d93-8e68-fe25a58525e9`、`01a01987.../01a0221a-43f4-7e02-a536-12ac4a31b386`、`01a00d5a.../01a0178e-16df-7260-819b-29b5b214358b`。

**具体问题。** 没有外部用户一度被当成继续开发的硬前置；相反，真实 Runtime 上的 development-only 缺陷场景又可能被误写成自然用户失败。

**项目所有者原话。** “真实用户只有我自己……不能说缺乏真实证据，下一阶段就停止推进了。”并指出任务是否真实“关键不在于任务由谁提出”。

**回答形成的方案。** 分开 scripted mechanism、controlled/simulated、项目所有者实际使用和外部用户泛化证据。开发者可以从真实 backlog 提出自然任务，条件是任务本身有价值、标准事前冻结、结果未知且不挑重试。development-only 使用独立命名空间和永久标签。

**可迁移方法。** 对每份证据先记录来源、执行路径、评价者和适用范围，再声明结论。真实性不是一个布尔值：真实 Runtime 不自动等于真实用户效果，模拟评价也不自动等于虚假执行。

**边界。** controlled evidence 足以完成工程闭环和单用户项目决定，不能证明多用户泛化；缺少外部用户也不能阻塞 v0.1 收口。

### 2.9 评测控制器不能替被测系统完成任务

**来源。** `01a00d5a.../01a017a6-a815-7322-9dcd-fffed4e6c12b`、`01a00d5a.../01a01792-75f8-7041-92bd-712c1415a006`、`01a00d5a.../01a0100d-6388-7541-a292-6a9c3c18d522`。

**具体问题。** 为了跑通候选链，监督会话容易自行写产品、修失败结果或手工生成 Candidate；过于复杂的试验项目又会让失败无法归因。没有候选时，还可能因为“不允许先修改 Skill”而形成无法获得改善数据的死循环。

**项目所有者原话。** “记得区分是测试天问而不是让会话自己写，会话只负责观察天问运行过程中的记录和问题。”

**回答形成的方案。** 控制器只冻结任务、启动、观察和判门；产品输出必须来自 Tianwen 的可审计 Action。选择范围小、真实有用、客观可验收的任务。假设先通过临时实验参数或隔离 Challenger 获得数据，不修改正式 Skill。

**可迁移方法。** 评测前明确 system under test、控制器、执行者、verifier 和 evaluator。任务、标准、条件与角色在运行前冻结；基础设施故障单独分类，不能混入产品成绩。

**边界。** 控制器可以修评测设施，但修复只能进入新版本和新活动，不能在同一次正式结果中补作业。

### 2.10 真实失败保留现场，先分类再开新周期

**来源。** `01a01987.../01a027bc-6b40-7551-8679-1beee3a6895f`、`01a00d5a.../01a01514-94fd-75f3-9a4a-44a6571c6362`。

**具体问题。** Stage 7 核心链不复杂，但首次端到端运行连续暴露安装、平台、transport、Skill scope 和 ledger 共存等外围缺口；单元测试曾掩盖真实 producer-consumer 断链。

**项目所有者原话。** “为什么我感觉这个阶段花了很长时间？”此前在解析器问题上又指出：“感觉这是个低级错误，然后没有考虑问题的根因，就给出了低级的方案？”

**回答形成的方案。** 分开核心实现和 operational proof 两个里程碑；正式尝试只有一次，旧结果永久保留。失败先区分产品缺陷、fixture 缺陷、操作脚本缺陷和外部基础设施；设计前用只读探针消除便宜假设，最终仍由真实产品入口承重。

**可迁移方法。** 不可逆或有成本运行前先消除可消除的不确定性；失败后保存、定位和重新分期，不靠重试覆盖。局部外围问题不能模糊核心功能已经或尚未完成。

**边界。** 普通网络 push 可以有有界重试，但不能把这一授权外推到 Provider、Goal 或正式评测重跑。

### 2.11 对话发现隐藏约束，文档保存可执行决定

**来源。** `01a00d5a.../01a00dcd-0a20-7640-b94c-9c0ca835b523`、`01a00d5a.../01a01021-27e6-77e1-987b-1b8e5dc72660`、`01a00d5a.../01a01030-e665-7012-8797-49cac94dd62a`。

**具体问题。** 一次性生成“完整方案”会自行补齐大量未声明假设；聊天中确认的新规则又可能只留在摘要索引，实施时无法区分已有设计、新建议和参数。

**项目所有者原话。** “如果是对话中决定，你给的方案就会更加有道理，但是如果是直接生成，有时候就会生成一些不太合理的方案。”以及“避免出现会话里面讨论过了，但是项目文档记录不够详细。”

**回答形成的方案。** 对话只讨论真正影响方向的隐藏约束，监督负责具体方案；收敛后统一落文档。文档采用三层：架构原则、可被证据修订的默认策略、计划或配置中的实现参数。每条默认规则说明默认行为、理由、例外和验证证据，并标明是继承决定还是本轮新增。

**可迁移方法。** 对话不是审批仪式，而是暴露目标、反例、体验底线和隐含假设的架构测试。文档不是聊天摘要，而是可供后来实施者执行和审查的决定。

**边界。** 不为每个问题创建孤立文档；一组相关问题先讨论收敛。实现细节不应塞满架构正文。

### 2.12 用户掌握方向，监督承担方案责任

**来源。** `01a00d5a.../01a00feb-27ef-7ce2-93c8-fd1b528c8133`、`01a00d5a.../01a00f21-3728-7c03-92de-eec71ab9b6ea`、`01a01987.../01a01eb8-3778-7630-a020-46a1b3417b51`。

**具体问题。** 工程节点被逐项交给项目所有者确认，用户只能反复回答 `ok`；另一方面，技术文档和汇报又钻入字段与状态机，难以把握总体设计。

**项目所有者原话。** “不需要一项一项找我确认，我只负责确定方向，具体方案实施你根据文档自己细化。”

**回答形成的方案。** 用户决定顶层目标、产品边界、重大价值取舍、授权扩展和 Promotion；监督自主决定文件、接口、测试、修复和边界内运行。面向用户先讲发生了什么、推荐什么、为什么、拒绝什么和代价，不从字段开始。

**可迁移方法。** 先判断谁拥有决定。方案问题由监督承担，不把不确定性转嫁给用户；只有方案会反过来改变架构或授权时再请求裁决。

**边界。** 自主细化不能让实施者发明新架构或降低验收标准。

### 2.13 控制器主动汇报，不用轮询表演持续工作

**来源。** `01a01987.../01a02236-b1f4-77e2-8d1a-68d457921753`、`01a01987.../01a01f54-99c5-7d70-a6f9-6a45c86f7a5e`、`01a01987.../01a01f69-d6a8-76d1-9902-29d78335685e`、`01a00d5a.../01a01850-7f07-72c1-ad5b-9fe822db6eef`。

**具体问题。** 执行任务完成小步骤后静默停下，监督者只能追问；反过来，Goal/Wait 机制又造成频繁轮询和上下文消耗。

**项目所有者原话。** “你可以等会话结束向你汇报，不用一直监控进程。”

**回答形成的方案。** 执行控制器在成功、停止和 blocker 时主动结构化汇报；监督等待事件，不高频读取。一个 blocker 只冻结相关路径，授权范围内的独立工作继续。Goal/自动唤醒不是流程必需品，不能为了“持续”而机械使用。

**可迁移方法。** 持续推进由明确的任务所有权、主动回报和下一入口保证，不由轮询频率保证。使用工具要解决实际协调问题，而不是作为进度表演。

**边界。** 对确实需要实时监控的高风险长操作可以使用有界监控；普通代理工作优先等待主动状态变化。

### 2.14 原型按资产类型处置，不受沉没成本支配

**来源。** `01a00d5a.../01a018cf-ca42-7890-b322-153521b3c71e`、`01a00d5a.../01a018c1-efb8-7823-a887-29761d6fab5b`、`01a00d5a.../01a01924-1efc-7d42-8091-9e22e90c6c59`。

**具体问题。** Python Alpha 已投入大量代码和真实运行，继续修会成为第二 Runtime，整体丢弃又会损失任务包、verifier 和失败证据。

**项目所有者原话。** “那前面的内容算是白写了吗？整个 alpha 分支？”以及“感觉好像越改越崩。”

**回答形成的方案。** 把成果分成四类：直接保留的产品能力、继续使用的验证资产、保留的设计认知、明确不进入产品的实现路线。冻结 Alpha，不整体合并也不删除；从中提取必要合同到 DSH 产品线。

**可迁移方法。** 不按投入量决定保留。原型完成的是降低不确定性的任务；路线被否决后，代码、证据、知识和错误方案可以有不同归宿。

**边界。** 只有仍能证明当前合同的资产才保留为门禁；历史实验不能继续冒充产品 Runtime 或当前完成证据。

### 2.15 阶段收口保留核心证据，不永久保存完整环境

**来源。** `01a00d5a.../01a01acb-087e-7bf1-be71-2e3ed5336054`、`01a00d5a.../01a01cb5-ebf4-7a40-9767-24613fc27be7`、`01a01987.../01a01d8f-a6f6-77f0-b504-6af7a45966f7`。

**具体问题。** 为可审计长期保留一次性工作树、Trial 现场、探针环境和多套缓存，导致 D 盘和流量持续增长；目录表面大小又因 hardlink 被误加总。

**项目所有者原话。** “这些需要清理的文件，先迁移到 E 盘的待清理文件夹……用了一周没有什么问题，再清理。”

**回答形成的方案。** 运行中保留现场；复审后提取 receipt、摘要、hash、必要数据库和 Git 提交；已推送且可重建的工作树、依赖和容器按正规机制移除。高不确定文件先迁入带清单和删除日期的隔离区。统一复用 `D:\DevData` store，区分共享缓存总量和本阶段增量。

**可迁移方法。** 可审计的目标是结论可追溯、关键事实可验证，不是所有字节永久在线。清理前按“正在使用、不可替代证据、已提交可重建、纯缓存”分类。

**边界。** 脏工作树、未推送提交、活跃数据库和系统文件不能按普通生成物处理；破坏性清理需要精确目标和可恢复步骤。

### 2.16 用有限、可展示的证据闭环定义项目完成

**来源。** `01a00d5a.../01a0190f-a1ba-7421-b6b2-28927a5a1da8`、`01a00d5a.../01a00e40-0144-77a3-bb74-13d24e956b0d`、`01a00d5a.../01a00e87-c777-7661-a58d-3dcc99ba752d`。

**具体问题。** 项目投入大量门禁、分支和设计，却缺乏用户可理解的最终成果；“通用自主学习 Agent”又没有现实完成边界。

**项目所有者原话。** “我现在不知道这个项目做完有什么意义了好像……对我而言，这个项目完成，能有什么好处吗？”

**回答形成的方案。** v0.1 只需真实证明一条闭环：真实任务 → 可归因问题 → Candidate → 公平评测 → future-run-only 生效 → 回滚，并形成演示、简洁架构图和诚实报告。到此收口，让后续真实反馈决定是否扩张。

**可迁移方法。** 平台型项目必须提前定义一个有限、可证伪、可展示的完成主张。内部工程完整性不能替代外部可理解的产品证据。

**边界。** v0.1 证据只能支持有限任务和单用户项目结论，不宣称 AGI、市场泛化或生态采用。

## 3. 从问答确认的 Tianwen 产品不变量

以下是产品专属结论，不应全部上升为跨项目个人 Skill：

| 不变量 | 问答形成的含义 | 当前处理 |
|---|---|---|
| 唯一 Runtime | DSH rc.7 负责模型、Agent Loop、工具、Session、恢复和普通 Goal | current canonical |
| Tianwen 定位 | 围绕 Agent 的长期 Goal、Evidence、学习和能力版本治理控制面 | current canonical |
| 一个执行底座 | EXECUTION、LEARNING、EVALUATION 是任务目的，不是三套 Agent | current canonical |
| Outcome 先于学习 | 业务结果先进入 Observed Gap 分诊，少量问题才变成 Signal | current canonical |
| 学习默认旁路 | 当前用户 Goal 不因可复用问题暂停；Candidate 只影响未来新 Run | current canonical |
| 能力发现不等于学习 | 首次优先发现和基线使用现有 Skill；持久适配需要真实结果 | current canonical |
| 两条学习路径 | 经验总结与假设探索围绕同一 Case 往返，直到有证据或停止 | current canonical |
| 受控实验桥接证据 | 临时任务参数或隔离 Challenger 可以取数，不能直接改正式 Skill | current canonical |
| 宽假设、窄候选 | 多想法先经有限实验；正式 Candidate 数量保持很小 | v0.1 采用固定单 Candidate 主线 |
| 一个候选一个核心假设 | 多规则组合需显式新 Candidate 和重新评测 | current governance principle |
| 独立评价 | 执行者不评价自己；客观 verifier 与主观 blind evaluator 分工 | v0.1 design |
| 用户批准边界 | 用户批准 Promotion 和真正越界动作，不逐轮批准工程细节 | current supervision contract |
| 证据分级 | fixture、controlled、所有者使用、外部用户泛化不得混写 | v0.1 design |

- 10 分钟价格快照、TTY 确认、固定 8/10 次请求和多层 recovery；

保留它们的理由只限于解释决策演变、验证某个历史失败或防止重新采用已否决路线。

## 5. 对当前监督方式的直接要求

1. 面向项目所有者先用故事和流程说明整体关系，再解释必要术语。
2. 每次汇报回答：发生了什么、推荐什么、为什么、拒绝什么、代价和下一入口。
3. 设计写明继承决定、当前缺口、新增决定和明确延期。
4. 对承重方案增加 architecture-fitness review，再进入 correctness review。
5. 用户介入时优先检查方向偏移或方案合理性，不把它只记录成一个偏好。
6. 历史审计必须保留用户推理和回答形成的方案，不生成关键词错题本。
7. 控制器在成功、停止或 blocker 时主动汇报；监督不靠高频轮询维持进度。
8. 只让已证明、当前可达的问题阻塞；其他独立工作继续。
