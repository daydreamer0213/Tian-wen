6. **stop：** 每一阶段插入 Provider/tool/persistence/identity/workspace/root/pointer fault，证明首个
   failure 后无下一 Agent/请求，且不 continuation partial activity。

### 9A4-R6 修正 parent monitor 的 Node 进程/流收尾语义

- R5 唯一一次 outer official installed Tianwen CLI 诊断仍在 15 秒后以 `ETIMEDOUT` 停止，stdout/stderr
  均为空，且没有 Session 或 Evolution ledger。R4 对同一 official install、DSH bin、Profile、patch、
  manifest、测试凭据和 loopback Provider 隔离的 direct child 已在 15 秒内正常退出并返回经既有 parser
  验证的 `selection-mismatch` receipt。只读逐字段对照没有发现 executable、argv、environment、cwd、
  DSH identity 或 patch identity 的语义差异；当前唯一新增语义层是 Tianwen 自建的、无限等待 child
  `close` 才解析回执的 parent monitor。
- 这是 official `tianwen controlled-lifecycle` 入口的真实可用性 blocker，但范围只到 child transport；
  不得再检查或修改 installer archive、runner、loader、评测 reducer、Agent loop、Provider、Session/
  Evolution ownership。R4/R5 已足以排除这些方向，不得用新的长 E2E 反复碰运气。
- 保留异步 `spawn()`：正式 lifecycle 是长运行前台命令，仍需正常的事件循环与取消/信号语义，不改成
  `spawnSync()`，也不新增 dependency。问题在收尾条件，不在异步启动本身。
- Node 的 child `close` 不只代表 OS child 已退出；它还等待 stdout/stderr 的底层 pipe socket 都完成
  `close`。当前实现因此把业务完成额外绑定到 Windows pipe teardown。最小修正为分别记录 child `exit`、
  stdout `end`、stderr `end`，三项齐全后才按现有 parser 与 exit-code 合同 finalize；不再以 child
  `close` 作为唯一完成信号，也绝不能仅在 `exit` 时提前解析尚未读完的输出。
- 保留现有 exact executable/argv/env、`shell=false`、pipe、64 KiB 上限和 safe failure；spawn/stream error、
  signal、overflow、非法/多行 stdout、任何 stderr、digest 不匹配或 receipt/status 不一致都继续 fail
  closed。合法结果仍经 `parseControlledLifecycleChildReceipt()` 验证并重新序列化，不直接转发
  child-controlled bytes。完成后只做局部 listener/stream 释放，不建设通用 child-transport 框架。
- 先在 `controlled-lifecycle-command.spec.ts` 建精确 RED：fake child 写合法 stopped receipt，随后
  stdout/stderr `end` 并 emit `exit(1)`，但故意永不 emit child `close`；当前 promise 必须被证明仍 pending，
  修正后应只转发一行并返回 1。再冻结乱序到达：exit 或两条 EOF 任一缺失时不能 finalize；EOF 前追加
  第二行或任意 stderr 仍 fail closed；正常 success/stopped、overflow 与 error 既有合同保持。
- 不添加整段 lifecycle timeout。若真实流连 `end` 都不产生，focused 诊断必须停止并回报，不能用 timer、

### 9A4-R6 复审闭合：异常 child 回收、fresh state owner 与长门授权

### 设计依据

- canonical 7.2 的“先采用标准语义，再发明低层协议”适用：DSH 将 patch 作为 UTF-8 YAML
  读取，CRLF 与 LF 对该配置语义等价。
- installer 的 raw archive 合同只要求同一次 Windows installer 调用中的两次 pack 字节一致；它
  没有定义跨平台 archive digest，也没有定义 patch 必须使用 LF 的字节合同。
- 因此该失败不是 Runtime、Agent、lifecycle 或 installer 产品语义缺陷，而是测试把平台换行表示
  锁成了不存在的产品合同。

### 方案比较与决定

- **采用：** 只在 `runtime-bundle.spec.ts` 现有 `readFileSync(..., "utf8")` 结果上调用
  `.replaceAll("\r\n", "\n")`，随后继续与原有完整 LF template 做 exact equality 比较。
- 该比较仍拒绝 bare CR、UTF-8 BOM、内容、顺序、缩进、空行和尾换行的任何变化；只把标准 CRLF
  表示归一为 LF。
- **拒绝：** `.trim()`、`\r?\n` 宽泛正则、YAML parse、新 helper 或通用换行 framework；这些方案
  会弱化完整文本合同或增加不必要结构。
- **拒绝：** `.gitattributes`。当前没有跨平台 byte contract；强制 checkout 字节会改变 Windows
  pack、installed bytes 与 receipt digest，却仍不能让整个 archive 在跨平台间 deterministic。
