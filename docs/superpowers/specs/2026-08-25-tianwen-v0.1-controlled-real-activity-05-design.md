## 1. Product goal

Activity-05 answers one product question: after the verifier-verdict ownership repair, can the
official freshly installed Tianwen product complete the existing real controlled lifecycle?

The required product path is:

```text
fresh official install
-> confirm offline readiness
-> activate deepseek-official/deepseek-v4-pro
-> confirm DeepSeek selection
-> invoke controlled-lifecycle exactly once
-> accept its first terminal result
-> restore offline
-> confirm offline
```

The primary result is the lifecycle receipt and the governed Session/Evolution state it leaves.
Archive formatting, path inventories and additional forensic machinery are not the goal.

## 2. Why a fresh installation is required

Activity-04 is terminal. It reached D1 and proved that the installed topology could lose the
optional structured error code even though the verifier result remained a durable error. Its
product predates the repair and contains partial Session/Evolution state, so it cannot prove the
new code.

Activity-05 therefore uses a new official installation rooted at:

```text
D:\DevData\tianwen-controlled-real-activity-05-product
```

The new installation must come from the exact reviewed main. No installed byte is patched in place.
Activity-04 and earlier products remain immutable history.

## 3. Functional ownership

The verifier is the owner of the semantic `met` or `not-met` decision. The durable Session Evidence
independently proves that the exact verifier call and result were committed. Learning Intake may
write the Outcome only when those two facts agree. This same rule must hold for seed, B/C evaluation,
Shadow and transition runs.

DSH remains the only owner of Agent execution, model calls, tools and Session persistence. Tianwen
Runtime/Evolution remain the owners of Outcome, Skill-use, evaluation and pointer facts. The
operation introduces no replacement runner, retry loop, transaction layer, checker or telemetry
system.

The operation creates 20 new non-nested workspaces and 25 new Session IDs in the `activity-05`

## 6. Readiness and operation state machine

The official installer runs once. Its canonical JSON receipt, archive digest, installed launcher and
18-file Runtime Bundle publication must agree before any model command. The first official status
must report offline selection, configured credential reference, zero request delta and no durable
Session/Evolution activity.

Model activation is setup and does not consume Activity-05. The first direct official
`controlled-lifecycle` invocation consumes it.

```text
uninstalled
-> installed-offline
-> deepseek-selected
-> lifecycle-invoked
-> passed | stopped | transport-failed
-> offline-restored
```

Each product command runs at most once. Setup failure skips lifecycle and restores offline once where
safe. Once lifecycle starts, its first result is permanent; no missing role, task or Session is
supplemented and no command is replayed.

## 7. Operation materialization

A one-use generator may create only the new operation root, 20 workspaces, manifest and freeze
receipt. It uses the tracked production manifest parser for the semantic digest and the tracked
Evidence canonicalizer for the workspace-set digest.

The generator may reuse the already reviewed generator structure as a code template, but all
Activity-05 roots, workspace names and Session IDs are regenerated and all embedded task/Skill bytes
are checked against the Git authorities above. It must not read any prior operation manifest,
Session, Evolution ledger or model result. It is not product code and is never rerun after target
execution begins.

## 8. Functional result

A successful lifecycle must return one valid `passed` receipt with:

- 25/25 roles: 2 seed, 10 B/C, 5 evaluator, 5 Shadow and 3 transition;
- D1 `not-met` with one Ticket and D2 `met` counterevidence;
- controlled evaluation and all five Shadow tasks passed;
- Promote, Rollback and Restore verified;
- pointer `B@rev1 -> C@rev2 -> B@rev3 -> C@rev4`;
- final official status restored to offline with zero model request delta.

A valid `stopped` receipt is a genuine failed product result and remains terminal. A transport failure
is also terminal. Both still require the one-time offline recovery sequence.

## 9. Evidence boundary

Report only:

- receipt-certified fields from official installer, model and lifecycle receipts;
- durable-observed Session and Evolution facts already written by the product;
- filesystem-observed identities required to establish the fresh installation and operation;
- `unknown` where no product or independent fact source exists.

Provider-account request count and actual tool-body execution count remain unknown unless an
existing independent source proves them. Raw prompts, model output, tool arguments/results,
reasoning, Skill content, credentials and raw errors are not copied into the report.

No checker, postmortem, probe, smoke, dry-run, budget service or retry framework is added.

## 10. Release boundary

Repository changes for Activity-05 are limited to this design, a concise execution plan and one
identity packet. They must enter main through a normal feature push and no-ff merge. The matching
automatic exact-main push attempt 1 must have Python, TypeScript and installer-windows all successful
before the official installer or any real Provider action.
