# Main-session learning status and recovery

## Demonstrated problem

In genuine acceptance Session B, a natural request to continue learning did not
match the cold-start resume regex. The main model could only see history counts,
mistook unchanged analysis counts for no evaluation activity, and repeatedly
messaged an already-submitted analyst. Actual governance had failed before any
evaluation arm, with the safe code `tool-surface-mismatch`. The analyst neither
owns evaluation nor needs additional permissions. The Candidate, feedback and
protocol are retained.

## Decision

Expose the existing governance owner and safe per-main audit through the existing
read-only status tool. Add one main-only native continuation tool that delegates
to the existing exact-parent recovery lane. This allows the model to interpret
ordinary language without teaching a growing list of command phrases. Keep the
old short-message and native goal-resume entry points for compatibility.

No generic intent classifier, new scheduler, new durable store, new analyst
permissions or historical record rewriting. This does not fix the separate tool
schema preflight defect and cannot override its gate.

## Contract

- Status remains read-only and bounded. Add `currentSession.learning` with
  `owner: "tianwen-runtime"`, current-main audit items from `projectLearningAudit`,
  at most eight items in its existing newest-first order, and `truncated`.
- Explain that the analyst proposes changes only; Runtime evaluates/activates;
  counts do not show evaluation progress; messaging an already-submitted analyst
  cannot resume evaluation. Unexposed failure detail remains unavailable.
- Native `tianwen_learning_continue` takes no arguments and is exposed only on
  ordinary main Sessions, using the same root/excluded-controlled checks as the
  existing status tool. It never accepts another Session or analysis identifier.
- It calls the existing lane for this exact live main lifecycle, only if current
  consent/support remains valid and the analysis has resumable pending work.
  It returns a bounded acknowledgement, not a promise of successful evaluation.
- Missing loop service or no valid pending work returns an honest no-op. Repeat
  calls use the existing lane coalescing; they cannot replay a completed arm,
  create a new Candidate, promote directly or give the analyst evaluation tools.
- No new consent or notice is generated by status/continue. No current model,
  tool allowlist, frozen task/Skill/Candidate/protocol or real evidence is edited.

## Verification

Test-first focused status, root/child/controlled scope, exact-parent recovery,
revoked support, terminal no-op and repeated scheduling behavior. Verify status
does not mutate the ledger or request models; verify recovery uses the retained
analysis rather than starting a replacement. Independently review before the
next diagnostic bundle. Real UI acceptance then uses the original natural
continuation wording, with the retained Candidate and ordinary configured model.
