## 1. Goal and evidence position

Activity-03 is the real-provider regression activity for the repaired controlled seed core path. It
reuses the Activity-02 authority without changing any experimental material:

- the same 15 tasks and byte-exact input/case material;
- the same hidden references, B/C Skill content, rubric, Provider and model;
- DeepSeek retry policy `normal/0` and disabled `session-title-llm`;
- the same tool surface, authorization, verifier and stop contracts.

Only product, evidence, operation, workspace and Session identity change. Activity-03 does not tune
questions to the repair, fit answers to a desired result, or become a second effects experiment. Its
purpose is direct attribution: run the same frozen authority through the repaired seed boundary in a
fresh isolated product.

The formal operation evidence labels remain exactly:

```json
{
  "source": "configured-provider-capable",
  "environment": "development-only",
  "defect": "synthetic-defect",
  "naturalUserEvidence": "not-claimed",
  "externalUserEvidence": "not-claimed"
}
```

These labels do not claim natural-user improvement, external-user effect or market generalization.

## 2. Chosen approach and rejected alternatives

The chosen approach is **the same tasks with entirely fresh isolated identity**. This changes only
the execution substrate required to avoid contaminated state, so a different seed outcome can be
attributed to the reviewed seed repair rather than to changed material.

The following alternatives are rejected:

1. Reusing the Activity-02 partial product or roots. Activity-02 is consumed, contains partial
   ledger facts and is permanent read-only evidence; reuse would contaminate attribution.
2. Replacing the task set. New tasks would mix task variation with repair validation and would no
   longer be a direct regression of the failed activity.
3. Adding another checker, postmortem, probe, telemetry layer, budget system or retry framework.
   Product-native fail-closed preflight already owns readiness at the source boundary.

## 6. Readiness gates and one-shot command order

Before any Activity-03 product operation, this design, its packet and its implementation plan must
form one reviewed feature exact SHA. That authority must enter `main` through controlled integration,
and the matching new automatic exact-main `push` attempt 1 must finish with Python, TypeScript and
installer-windows all successful. The current seed repair main and run are completed prerequisites;
they are not the future Activity-03 operation authority or CI identity.

The fixed readiness sequence is:

1. Product, install-evidence and operation roots are all absent.
2. Run the official installer exactly once into the new product root. Verify its ready receipt,
   archive digest, canonical official launcher identity and all 18 published entries as regular,
   independent identities with no source hardlink.
3. Through `receipt.binDir`'s official `.CMD`, run official model status exactly once. It must prove
   the offline selection, configured credential reference and `modelRequestsDelta=0`, with fresh
   Sessions and Evolution state.
4. Run the exclusive-create generator exactly once. Independently close 15 tasks, 20 workspaces,
   25 Sessions, manifest file digest, semantic manifest digest, workspace-set digest, generator
   digest and freeze receipt.

Only after all readiness facts close may the formal sequence run, with these exact argument vectors:

```text
model use --model deepseek-v4-pro --data-dir ABS_PRODUCT --json
model status --data-dir ABS_PRODUCT --json
controlled-lifecycle --manifest ABS_MANIFEST --data-dir ABS_PRODUCT --json
model use --model offline --data-dir ABS_PRODUCT --json
model status --data-dir ABS_PRODUCT --json
```

Every command uses the official `.CMD` resolved from the install receipt, PowerShell's call operator
and a tokenized argument array. stdout and stderr use distinct, non-overwriting evidence targets, and
the exit code is saved immediately after each invocation. Command strings through `cmd /c`,
`Invoke-Expression`, nested shells, positional shorthand, smoke, dry-run and Goal are forbidden.

The first direct official DeepSeek `model use` invocation consumes Activity-03. The lifecycle command
may be invoked exactly once. After lifecycle success, stopped receipt or transport failure, offline
model use and final model status each run exactly once. A failed recovery command is preserved as its
one result and is not retried.

## 7. Product-native preflight

The sole lifecycle invocation must close all of the following before the first Agent, Provider/model
request or tool body:

1. production parsing of the frozen manifest digest and settlement of installed loader/services;
2. empty Evolution state, ledger, Champion and controlled pointer;
3. configured Session root identity, installed persistence `list()` returning no persisted Session,
   and zero live Session and Agent;
4. real containment and frozen snapshots for all 20 workspaces;
5. configured credential reference and exact `deepseek-official/deepseek-v4-pro` selection;
6. exact call configuration with retry `normal/0`;
7. exact command-scoped tool surface;
8. exact parent B Skill identity in every required workspace scope.

Any mismatch stops before external activity. Activity-03 does not claim a separate
`0/0/0/0/0` checker attestation and does not add a second readiness command.

## 8. Success contract

Success requires one valid `passed` controlled-lifecycle receipt and all of these facts:

- `25/25` formal roles closed;
- D1 is `not-met` and produces one Ticket; D2 is `met` counterevidence;
- controlled evaluation passes;
- all isolated Shadow tasks pass;
- Promote, Rollback and Restore are verified;
- the governed pointer follows
  `B@rev1 → C@rev2 → B@rev3 → C@rev4` and ends at `C@rev4`;
- final official status proves offline, configured credential reference and
  `modelRequestsDelta=0`.

A passed receipt certifies only its exact schema fields and reductions. Unless an independent source
exists, Provider-account request count and actual tool-body execution count remain `unknown`; they
must not be inferred from Session events or receipt aggregates.

## 9. Failure and evidence boundaries

If any readiness step fails, preserve the new Activity-03 scene and stop before formal model use.
Installer, generator and readiness status must not be silently rerun, repaired or replaced.

After the first formal model use, any nonzero exit, invalid or multiline receipt, schema mismatch or
transport failure means Activity-03 is consumed. The frozen stop line determines which later formal
commands are skipped; offline use and final status still run at most once where safely possible.

The single lifecycle result—`passed`, `stopped` or transport failure—is permanent. No task, arm or
Session may be supplemented; no result may be selected away; there is no retry and no automatic
Activity-04.

Evidence is classified into four levels:

- `receipt-certified`: exact finite facts from a valid official product receipt;
- `durable-observed`: facts read from successfully persisted product state;
- `filesystem-observed`: finite external read-only observations of file identity, type or digest;
- `unknown`: facts without a valid receipt or independent source.

Session model-step or tool-call events are not Provider-account requests or proof that a tool body
actually executed. Public summaries must not include raw prompts, model output, tool arguments or
results, evaluator reasoning, Skill content, runtime Session/Run/Candidate IDs, paths, credential
values or raw errors.

When stopped, evidence is limited to the official safe receipt, already persisted product facts and
finite outer read-only snapshots labelled `filesystem-observed`. Activity-03 does not run a checker
or postmortem.

## 10. Scope and YAGNI boundary

This design changes no `packages/**` source, workflow, installer, CLI, Profile, dependency or
lockfile. It adds no model, token or CNY cap; no retry, scheduler, database, telemetry, generic
workflow framework or second Agent loop.

An operations handoff may be written only after Activity-03 reaches its unique terminal result.
README and other public status documents must not claim Activity-03 success before that result exists.
