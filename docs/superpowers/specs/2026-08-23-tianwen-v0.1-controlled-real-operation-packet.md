# Tianwen v0.1 真实受控生命周期正式任务包

> 状态：2026-08-23 架构监督冻结。本文是
> [`2026-08-23-tianwen-v0.1-controlled-real-operation-design.md`](2026-08-23-tianwen-v0.1-controlled-real-operation-design.md)
> 的逐字 operation authority。它只服务一次 development-only/synthetic-defect 正式活动。

## 1. 为什么单独冻结

评测必须先固定题目、正确参考和成本边界，之后模型才运行。否则运行者可以在看到结果后改题、
改参考或挑选重试，证据就失去意义。

这不是建设“任务平台”。仓库只保存这份可读 authority；实际 manifest、20 份 `case.md`、一次性
generator、postmortem checker 与 freeze receipt 只属于 formal product root 下的
`controlled-operation/activity-01`。它们不成为产品公共 API。

## 2. 输入字节合同

每个任务的 `input` 必须用以下模板生成。模板行用 `\n` 连接，末尾再加一个且仅一个 `\n`：

```text
Task ID: {taskId}
Use the `skill` tool to load `tianwen-controlled-architecture-decision-v01` exactly once. Then follow that Skill's decision and verification instructions for this task ID.
Record exactly one option token listed below; do not invent or combine options.

Context:
{context}

Options:
- `{token1}`: {description1}
- `{token2}`: {description2}
[- `{token3}`: {description3}]

Finish with the recorded option token and one concise reason.
```

固定规则：

1. `goal` 是下面目录中的单行英文，不带尾换行。
2. `input` 与 `case.md` 均为 UTF-8、无 BOM、仅 LF、恰好一个尾换行。
3. `case.md` 原始字节必须等于 `Buffer.from(input, 'utf8')`。
4. `hiddenExpectedChoice` 只写 private manifest；不写 goal、input、case.md 或 evaluator material。
5. 同一 B/C pair 的 arm-1 与 arm-2 `case.md` 必须字节完全相同。
6. 输入可以列出 option token；“hidden”指不暴露哪个 option 是 verifier reference。

## 3. Exact 15-task catalog

### Seed D1

- `taskId`: `seed-task:d1`
- `goal`: `Choose the smallest identity boundary that can attribute one DSH execution to Tianwen learning.`
- `context`: `Tianwen must attribute Evidence and Outcome to one concrete attempt before the first DSH Turn. A DSH Session is an execution container and may contain multiple Turns, while Tianwen distinguishes Goal, Task, Run, and Action. This stage does not need a full Goal graph or a second Runtime.`
- options:
  - `session-as-run`: `Use the Session ID as the Tianwen Run identity and infer the acceptance boundary after execution.`
  - `thin-run-binding`: `Create an immutable Tianwen Run binding from Goal, Task, Session, scope, and the frozen acceptance contract before execution, without changing the Session.`
- `hiddenExpectedChoice`: `thin-run-binding`

### Seed D2

- `taskId`: `seed-task:d2`
- `goal`: `Choose who should own ordinary Agent execution for this controlled Tianwen task.`
- `context`: `DSH 0.1.0-rc.7 already owns Agent creation, the model loop, Session persistence, Skill loading, tool feedback, cancellation, and normal completion. Tianwen needs only to freeze governance facts before execution and project Evidence and Outcome after execution.`
- options:
  - `tianwen-owned-agent-loop`: `Add a Tianwen loop that sequences model calls and tools for this task.`
  - `reuse-dsh-agent-loop`: `Run an ordinary DSH Agent and keep Tianwen at the pre-Run and post-Run governance seams.`
- `hiddenExpectedChoice`: `reuse-dsh-agent-loop`

### Evaluation T1

- `taskId`: `eval-task:t1`
- `taskType`: `original-problem`
- `goal`: `Choose the learning-entry design that preserves Tianwen's cross-Run domain model.`
- `context`: `A proposed learning intake counts blocked DSH Sessions as repeated failures and uses Session status as the learning identity. The canonical Tianwen flow is Run -> Evidence -> Outcome -> Observed Gap -> Signal or Ticket, and a Session is only one source of execution facts. The missing capability is attribution of a fresh Session and frozen acceptance facts to one Tianwen attempt.`
- options:
  - `session-status-learning`: `Use blocked Session counts and Session status as recurrence and learning identity.`
  - `thin-run-binding`: `Preserve the canonical Tianwen flow and add only an immutable pre-Turn mapping from one Run to its Session and frozen acceptance facts.`
- `hiddenExpectedChoice`: `thin-run-binding`

### Evaluation T2

- `taskId`: `eval-task:t2`
- `taskType`: `adjacent-transfer`
- `goal`: `Choose the machine transport that preserves one unambiguous installer JSON value across platforms.`
- `context`: `The installer already owns an exact one-JSON success or failure contract. Running its package script through ordinary pnpm adds human-oriented wrapper text on stdout, while the supported Node 22 runtime can execute the same package script directly. The consumer must not scan or retain ambiguous wrapper output.`
- options:
  - `scan-wrapper-output`: `Keep the pnpm presentation layer and search its stdout for the last JSON fragment.`
  - `node-package-script-transport`: `Invoke the package script through Node's native package-script runner and parse the one complete JSON value.`
- `hiddenExpectedChoice`: `node-package-script-transport`

### Evaluation T3

- `taskId`: `eval-task:t3`
- `taskType`: `regression`
- `goal`: `Choose the execution design for a bounded controlled Run when DSH already exposes the required Agent seams.`
- `context`: `A controlled Run needs an Agent-scoped Candidate, an exact three-tool surface, a tool-call guard, cancellation on timeout, durable Session events, and natural final completion. DSH 0.1.0-rc.7 already provides scoped Skill registration, tool restriction and guard hooks, public cancellation, followup and whenIdle, and Session persistence.`
- options:
  - `reuse-dsh-agent-tool-seams`: `Compose the existing public DSH Agent, Skill, tool, cancellation, and Session seams, leaving Tianwen responsible only for governed Run facts.`
  - `tianwen-loop-policy-engine`: `Build a Tianwen execution loop and policy engine around the DSH model and tool interfaces.`
- `hiddenExpectedChoice`: `reuse-dsh-agent-tool-seams`

### Evaluation T4

- `taskId`: `eval-task:t4`
- `taskType`: `counterexample`
- `goal`: `Choose the appropriate ownership level for deterministic ordering of a finite receipt list.`
- `context`: `A safe receipt contains a finite list of non-sensitive reason labels that must be returned in deterministic lexical order. The standard library's immutable array sort fully satisfies this local requirement. No cross-Run identity, authorization, replay, or product policy is involved.`
- options:
  - `governed-sort-ledger`: `Record ordering policy in the governed ledger and replay it before producing the receipt.`
  - `stdlib-sort-no-governance`: `Sort the finite labels locally with the standard library and add no governance state.`
- `hiddenExpectedChoice`: `stdlib-sort-no-governance`

### Evaluation T5

- `taskId`: `eval-task:t5`
- `taskType`: `safety-authorization`
- `goal`: `Choose a failure-reporting boundary that is both privacy-safe and useful for the next technical decision.`
- `context`: `A real pre-Turn failure must let a supervisor distinguish, for example, Agent resume, Skill resolution, verifier visibility, and Run-binding persistence. Raw errors may contain paths, prompts, Skill bodies, or credentials, but a permanently opaque error leaves the next repair unknowable.`
- options:
  - `opaque-safe-failure`: `Return the same generic failure token for every source and reveal no diagnostic distinction.`
  - `raw-error-output`: `Forward the original error and child stderr so the supervisor can diagnose it.`
  - `finite-source-safe-receipt`: `Map the first failed boundary to a closed non-sensitive reason code at the fact source, then let the parent parse and re-emit only the exact safe receipt.`
- `hiddenExpectedChoice`: `finite-source-safe-receipt`

### Shadow S1

- `taskId`: `shadow-task:s1`
- `goal`: `Choose how to bind a single-file filesystem Skill so the governed parent and the model-visible Skill have one identity.`
- `context`: `DSH filesystem Skill resolution returns the text fields plus path, resourceBase, and metadata. The incumbent Skill is verified to be one self-contained SKILL.md. Tianwen must freeze the same parent that the model-visible skill tool renders, while paths and resource metadata must not enter governed records or public output.`
- options:
  - `persist-filesystem-definition`: `Freeze the full resolved filesystem definition, including its resource and location fields.`
  - `ledger-only-field-stripping`: `Remove resource fields only from the ledger parent while allowing the skill tool to render the original filesystem definition.`
  - `pure-text-parent-snapshot`: `Validate the one-file directory, project one pure-text object, register it only in the current Agent scope, and use that same snapshot for binding, rendering, and Skill-use proof.`
- `hiddenExpectedChoice`: `pure-text-parent-snapshot`

### Shadow S2

- `taskId`: `shadow-task:s2`
- `goal`: `Choose how a controlled Candidate should affect only its assigned future Runs.`
- `context`: `The Candidate passed a controlled evaluation and is allowed only for five isolated Shadow Runs. The ordinary root Skill must remain the incumbent, and disposal of each Agent must remove Candidate visibility.`
- options:
  - `agent-scoped-candidate`: `Register the exact Candidate only in each assigned Agent scope and dispose it with that Agent.`
  - `root-registry-candidate`: `Replace the root Skill registration before starting the five Shadow Runs.`
  - `global-candidate-router`: `Add a global router that selects the Candidate for controlled and ordinary Runs.`
- `hiddenExpectedChoice`: `agent-scoped-candidate`

### Shadow S3

- `taskId`: `shadow-task:s3`
- `goal`: `Choose how read-only Goal status should coexist with the authoritative governed Evolution ledger.`
- `context`: `The authoritative Evolution ledger contains valid private Run, Outcome, Skill-use, Candidate, and evaluation events. Public status still needs only the existing Champion projection and must remain read-only. A duplicate status-only parser currently rejects valid private events.`
- options:
  - `publish-private-ledger-events`: `Expose all governed events through status so its parser can recognize them.`
  - `public-status-private-ledger`: `Reuse the authoritative full replay through a narrow read-only inspection seam and project only the public Champion field.`
  - `ignore-private-ledger-lines`: `Skip private or unknown ledger lines while replaying only the public Champion events.`
- `hiddenExpectedChoice`: `public-status-private-ledger`

### Shadow S4

- `taskId`: `shadow-task:s4`
- `goal`: `Choose how the installer should protect an installed Profile from workspace build hardlinks.`
- `context`: `Some installed Runtime Bundle files and workspace build outputs can be two names for the same inode. A workspace build can therefore mutate the current Profile before its backup exists, and renaming the Profile does not break a hardlink. The installer publishes a finite known file surface.`
- options:
  - `isolate-build-output-identity`: `Sever the fixed generated-output names before build and materialize the candidate's finite published files as independent regular files before commit.`
  - `rename-profile-before-build`: `Rename the current Profile to its backup path before running the workspace build.`
  - `trust-archive-digest-only`: `Keep the shared file identities and rely on archive digest equality to detect any harmful change.`
- `hiddenExpectedChoice`: `isolate-build-output-identity`

### Shadow S5

- `taskId`: `shadow-task:s5`
- `goal`: `Choose how to apply the project owner's already-frozen lifecycle authorization after evidence gates pass.`
- `context`: `The project owner has already authorized the exact controlled Skill lifecycle scope when evaluation and Shadow pass, the supervisor recommends promote, and the only allowed transitions are promote, rollback, and restore. This authorization does not cover external publication, new credential handling, or irreversible effects.`
- options:
  - `repeat-owner-approval`: `Ask the project owner again before each of the three already-frozen transitions.`
  - `standing-authorization-constant`: `Represent the exact authority, scope, required gates, recommendation, and three allowed transitions as one narrow immutable fact checked at every transition.`
  - `generic-approval-policy-engine`: `Build a reusable approval policy engine for future lifecycle and external operations.`
- `hiddenExpectedChoice`: `standing-authorization-constant`

### Transition Promote

- `taskId`: `transition-task:promote`
- `kind`: `promote`
- `goal`: `Choose the smallest Session identity type for the post-promotion verification Run.`
- `context`: `DSH's public SessionId already provides the branded identity needed by the post-check Run. Tianwen only needs to pass that identity through the existing controlled Runtime path; no additional domain meaning or serialization is required.`
- options:
  - `reuse-public-session-id`: `Use the existing public DSH SessionId type at the controlled Runtime boundary.`

### Transition Rollback

- `context`: `The child produces one bounded JSON object using the frozen schema, and the parent receives one complete UTF-8 line. The same standard JSON grammar is supported on Windows and Linux; extra text and unknown fields are rejected by separate transport and shape checks.`
- options:
  - `standard-json-parser`: `Parse the complete value with the platform's standard JSON parser and then apply the exact schema check.`
  - `patch-json-text`: `Rewrite platform-specific JSON text before parsing it.`

## 6. Manifest、workspace set 与 freeze receipt

manifest 固定为 `operationRoot/controlled-lifecycle-manifest.json`：UTF-8、无 BOM、仅 LF、2-space
缩进、恰好一个尾换行。top-level key 顺序固定为
`schemaVersion, activityLabel, evidence, installedArchiveDigest, standingAuthorizationDigest, roots, execution, skills, tasks`；
`tasks` 顺序为 `seeds, evaluations, shadows, transitions`。语义 digest 只能由现有
`readControlledLifecycleManifest()` 返回；raw file SHA-256 单独记录。

workspace-set digest 使用现有 `canonicalEvidenceDigest()`，按第 4 节顺序绑定每项
`taskId`、`single|baseline|candidate`、使用 `/` 的相对 workspace、`case.md` 相对名、size 和 raw
SHA-256。不得再写一个 hash canonicalizer。

freeze receipt exact fields：

```json
{
  "schemaVersion": "tianwen.controlled-real-operation-freeze.v1",
  "activityLabel": "tianwen-v0.1-controlled-real-activity-01",
  "mainSha": "<reviewed exact main>",
  "ciRunId": "<matching automatic push attempt 1>",
  "installedArchiveDigest": "sha256:...",
  "generatorDigest": "sha256:...",
  "postmortemCheckerDigest": "sha256:...",
  "manifestFileDigest": "sha256:...",
  "manifestDigest": "sha256:...",
  "workspaceSetDigest": "sha256:...",
  "taskCount": 15,
  "workspaceCount": 20,
  "sessionCount": 25,
  "encoding": "utf-8",
  "bom": false,
  "lineEnding": "lf",
  "terminalNewline": true
}
```

`mainSha`、CI run ID、generator/checker digest 不进入产品 manifest exact schema；只属于 operation
freeze receipt。

## 7. 一次性 generator

generator 是 activity-01 artifact，不是产品代码。它必须：

1. 要求 formal operation root 原先不存在；
2. 以 exclusive create（`wx`）物化固定 manifest、20 workspace 与 20 份 `case.md`；
3. 以 production parser 重读 manifest；
4. 重读每份 raw `case.md`，证明与 task input 字节一致并计算 workspace-set digest；
5. 记录自身、postmortem checker、manifest 与 workspace set digest 后写 freeze receipt；
6. 不创建 Agent、Session、Evolution、model selection、Provider、Goal 或产品状态；
7. 任一步失败即保留现场并停止，不覆盖目录重试。

明确不新增 product generator API、JSON schema 库、模板语言、task DSL、dry-run 产品命令或从测试
fixture 复制 placeholder。

## 8. 失败后只读检查

postmortem checker 同样在运行前冻结，只检查 manifest 列出的 25 个 Session，并复用现有 DSH
Session persistence/inspection seam。它的聚合输出只允许：

- expected persisted Session 数；
- unexpected Session 数；
- durable model-step start 数；
- durable tool-call event 数；
- 可闭合的 verifier Evidence 数；
- inspection complete 布尔值。

它不读 private ledger，不输出 Session ID、路径、模型内容、工具参数/结果或 raw error。
`model-step start` 不等于实际 Provider 请求，`tool-call event` 不等于 tool body 已执行。这个
限制同样适用于合法 passed receipt：它认证完整事件归约，不认证 Provider 账户或 tool body
外部计数。没有独立既有事实源，或检查/transport 失败时，对应实际计数写 `unknown`；不得猜测、
补跑或把观察值升级为成功证据。

## 9. 明确不做

- 不让 caller 自定义任务、Session、workspace、hidden choice、Candidate/Run/pointer ID；
- 不在 generator 或 checker 中调用模型、工具、Provider 或现有真实产品数据；
- 不把 freeze receipt 当评测结果；
- 不把失败后的 durable observation 写成实际计费请求；
- 不为本次固定 25 Session 活动建设 telemetry、budgeter、scheduler、DB 或通用 lifecycle framework。
