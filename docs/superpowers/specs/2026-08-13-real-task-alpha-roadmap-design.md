# 天问“真实任务 Alpha”分阶段路线设计

**状态：** 总体路线与 Alpha-A 详细设计均已获用户确认；Alpha-A 实施计划已完成
**日期：** 2026-08-13
**范围：** 把当前可审计的持续学习竖切，从协议样例推进到真实、可重复的小型仓库任务

**规范关系：** 本文决定 Alpha-A 至 Alpha-D 的证据顺序和阶段范围；学习类型、Observed Gap 分诊、受控实验、候选治理、授权、主观评测及 Skill 适配语义，以 `2026-08-17-tianwen-continuous-learning-governance-design.md` 为准。两份文档冲突时不得由实施代码自行选择，必须回到架构层修订。

## 1. 结论

真实任务 Alpha 不直接接入 SWE-bench，也不直接把用户的私人项目当第一块试验田。第一阶段采用五个“小而真实”的 Python 仓库任务：

- 模型必须读取和修改真实代码；
- 修改后必须执行真实程序检查；
- 最终结果由模型控制范围之外的固定验证器判断；
- 每次都从同一个已登记基线开始；
- 模型、Skill、工具、预算、环境和结果都留下可核对记录。

Alpha 分成四段：

```text
Alpha-A：真实执行
→ Alpha-B：同条件版本比较
→ Alpha-C：从真实问题形成学习候选
→ Alpha-D：保护评测、人工晋升和不同任务迁移
```

不能跳级。Alpha-A 尚未证明“天问会持续学习”，它只回答更基础的问题：天问能不能安全地完成真实任务，并留下足够可信的实践证据。Alpha-D 通过也不表示天问全部完成，只表示 `repo_task` 这个有限范围的首个持续学习竖切形成了可信证据；更广领域、长期运行、产品控制面和规模化能力仍属于后续阶段。

## 2. 为什么现在需要 Alpha

当前实现已经证明了这些基础合同：

- Goal、Loop、Task、Run、Action、Evidence、Checkpoint 可以持久记录；
- 顶层目标和发布权仍由人掌握；
- 本地与必要外部探索能够经过授权、预算和来源记录；
- PydanticAI + Harness 可以运行确定性模型和真实模型；
- DeepSeek V4 Pro 的原生 Provider 接入、离线合同和显式付费探针已经就绪；实际付费探针仍需用户凭据运行；
- `repo_task` Skill 有版本、候选、评测、晋升和回滚协议；
- 当前密封评测能够验证声明式 Skill 文本合同。

但是目前还没有证明：

1. 模型能在一个有真实代码和真实失败条件的仓库里完成修改；
2. 最终结果不是模型自己说“完成了”，而是独立检查得出的；
3. Champion 与 Challenger 的比较来自相同起点和相同条件；
4. 学习候选确实来自实践中观察到的问题，而不是预先写好的答案；
5. 候选在不同后续任务上仍然有效，而不是只记住触发样例。

Alpha 就是按这个顺序补齐证据。

## 3. 四段证据阶梯

### 3.1 Alpha-A：真实任务执行层

目标：

> 证明当前 Champion 能在隔离、可丢弃的小仓库中执行真实代码任务，并由独立验证器形成可信结果。

新增的最小能力：

- 不可变任务清单和仓库基线；
- 位于 `D:\DevData` 的一次性工作区；
- 只能按名字调用的固定容器检查；
- 模型结束后运行的独立最终验证器；
- 绑定任务、模型、Skill、基线、差异、验证结果和成本的 `TrialResult`；
- 一个明确的 Alpha 运行入口和通俗的过程展示。

Alpha-A 不创建 Challenger，不自动学习，也不晋升版本。

### 3.2 Alpha-B：同条件 Champion / Challenger 比较

目标：

> 证明两个行为版本可以从相同基线出发，在相同模型、预算、工具、容器镜像和验证器下比较。

关键要求：

- 每个版本使用独立工作区；
- 冻结完整模型标识和模型设置；
- 冻结 Skill、任务、检查器、环境和预算摘要；
- 同一任务不能把一个版本运行后的文件或上下文交给另一个版本；
- 报告正确性、安全边界、Token、工具调用、用户打断和时间；
- API 模型存在随机性时使用成对重复试验，不把单次输赢当结论。

Alpha-B 仍不要求系统真的生成一个好 Challenger；它先证明比较设施可信。

### 3.3 Alpha-C：从真实问题形成学习候选

目标：

> 只有真实执行中重复出现的问题、明确用户纠正或意外成功，才可以启动学习更新循环。

流程：

```text
真实 TrialResult / 用户反馈
→ Observed Gap 分诊
→ LearningSignal
→ Learning Ticket + Case
→ 原因已有证据：经验总结
  或原因不明：假设探索 → 受控 Experimental Run → 新 Evidence
→ 有前提和代价的 Lesson
→ 选择最窄修改范围
→ repo_task Skill Challenger
→ Alpha-B 同条件比较
```

能力发现和临时任务绑定仍属于 Execution 准备，不因为“找到了一个 Skill”就创建学习候选。Alpha-C 第一版只处理仓库内已冻结的 `repo_task` Skill，不接入外部 Skill 市场、动态安装或通用路由；但它产生的 Candidate、Evidence 和作用域语义不能与持续学习治理规范冲突。

如果实践证据没有支持可泛化的改进，合法结果是：

- 不创建候选；
- 记录证据不足；
- 把问题归到任务信息、工具、模型、验证器或其他层；
- 只保存用户或项目级偏好，不生成通用候选；
- 等待更多样本。

不能为了展示“会学习”而强行生成 Challenger。

### 3.4 Alpha-D：保护评测、晋升和迁移

目标：

> 证明候选不仅修好了触发任务，还能通过未参与候选生成的保护任务，并在人工晋升后改善不同的后续任务。

关键要求：

- 触发任务、开发任务和保护任务分开；
- 学习者不能读取保护验证器和参考答案；
- 保护评测逐步接入现有签名回执与 evaluator 身份隔离；
- 正确性、安全、越权和数据泄露是硬门，不能用平均分抵消；
- 首次晋升必须由人确认；
- 保留旧 Champion 和回滚入口；
- 晋升后必须观察不同后续任务；
- 发现回归时自动建议回滚，但不能静默改写用户目标。

Alpha-D 的首批代码任务主要使用客观验证器。未来加入风格、审美或满意度等主观任务时，必须把客观硬门、业务指标和用户偏好证据分开；模型评审只能辅助预检，不能替用户宣布满意。

完成 Alpha-D 才能谨慎声称：天问在这个有限任务范围内展示了持续学习证据。

所有阶段都继承原有 Goal 主权：任务清单、验证器和学习者只能报告目标不可行或建议调整，不能修改人类确认的顶层 Goal。扩大授权、改变价值判断或接受严重副作用仍由人决定。

## 4. 第一组五个任务

第一组任务使用小型、可运行、无私人数据的 Python 仓库。它们不是只检查一句固定文本的玩具题，而是要求修改代码并通过程序化验证。

| 编号 | 类型 | 主要观察点 |
|---|---|---|
| A1 | 修复真实测试失败 | 会不会先定位原因、做最小修复并验证 |
| A2 | 实现小功能 | 会不会把自然语言需求变成可运行行为 |
| A3 | 依据冻结参考资料做兼容修改 | 会不会先读取来源和适用条件，再改代码 |
| A4 | 局部修改并保持旧行为 | 会不会控制影响范围，避免“修一处坏一片” |
| A5 | 根据后续反馈做第二轮改进 | 会不会在同一用户 Goal 下吸收反馈，而不是重做或忘掉第一轮 |

A1 至 A4 各有一个执行轮次。A5 有两个顺序轮次：第一轮完成初始需求，第二轮收到预先登记的反馈样本；两个轮次共享 Goal 和工作区，但各自创建新的 Run，因此不会用新提示悄悄改写旧 Run。A5 的两轮目标、验收条件和第二轮反馈都在 Goal 创建前向用户展示并一次确认；控制器只是按已确认顺序揭示第二轮信息，不能临时改变 Goal。

A3 使用带来源 URL、读取日期和内容摘要的冻结参考材料，以保证重复运行时输入一致。实时网页探索仍属于天问能力，但不放进 Alpha-A 的首轮胜负条件，避免把网页变化、网络故障和代码执行问题混在一起。

Alpha-A 只落实用户目标循环中的真实任务执行，不新增第三种循环，也不声称已经开放用户 Loop 派生子 Loop。Alpha-C 再让“完善天问”元循环从允许进入 `meta_telemetry` 的 TrialResult 投影创建有限学习子 Loop；原始用户文件、完整轨迹和本地路径不会因此自动进入元循环。

## 5. 什么叫“真实”，什么还不算

这里的“真实”表示：

- 仓库中的程序真的会运行；
- 未修改基线确实不能通过最终验证；
- 参考解法确实能够通过最终验证；
- 模型修改的是实际文件，不是回答选择题；
- 最终验证由固定程序完成，不由模型自评；
- 失败、成本和越界同样被记录。

这里暂时不表示：

- 已经能处理任意大型开源项目；
- 已经达到 SWE-bench 或 Terminal-Bench 水平；
- 已经能安全运行任意陌生代码；
- 已经证明某个 Skill 普遍更好；
- 已经可以在用户私人仓库中无人值守运行；
- 已经实现模型参数训练。

## 6. 任务格式借鉴与复用原则

任务形状借鉴成熟基准的共同做法：

```text
任务说明
+ 固定环境与仓库基线
+ 模型无法改写的验证脚本
+ 可重复的结果记录
```

Terminal-Bench 公开任务同样由指令、验证脚本、参考解法和沙箱执行环境组成；SWE-bench 也强调固定仓库问题和独立评测。天问复用这些经过实践验证的结构，但首轮不直接引入它们的完整数据集与运行平台。

原因：

- SWE-bench 官方本地评测建议约 120 GB 可用空间、16 GB 内存和 8 核 CPU，首轮接入会把主要精力转成镜像与依赖工程；
- Terminal-Bench / Harbor 是完整基准平台，现阶段直接依赖会同时引入任务注册、适配器、沙箱和报告体系；
- 天问目前真正需要验证的是自己的 Goal、执行证据、学习归因和版本治理，而不是重新做一个排行榜。

后续如果真实证据表明 Harbor 的执行适配器比最小 Docker 入口更省维护，可以把它作为替代实现评估；上层 Task、TrialResult、Evidence 和比较协议不随之改变。

## 7. 隔离策略

Harness 的 FileSystem 能限制模型通过文件工具访问的目录；Shell 能过滤命令和敏感环境变量。但是 Harness 自己明确说明，Shell 的允许列表只是尽力检查，不是操作系统安全边界。

因此 Alpha 的代码执行采用两层：

1. 模型只通过 Harness FileSystem 修改一次性工作区；
2. 模型生成的代码只在受限 Docker 容器内运行，不在持有模型 API Key 的主机进程中直接执行。

首轮只复用 Docker CLI，不引入 Docker SDK、Kubernetes、Harbor 服务或自研沙箱。容器默认：

- 无网络；
- 不传 Provider 凭据；
- 工作区只读挂载；
- 验证器只读挂载；
- 根文件系统只读；
- 丢弃 Linux capabilities；
- 禁止获取新权限；
- 限制 CPU、内存、进程数和时间；
- 不挂载 Docker socket、用户目录或天问状态目录。

Docker 镜像和运行数据放在 `D:`。如果 Docker Engine 不可用，预检在发送付费模型请求之前停止，并明确报告环境不可用。

这仍不是处理敌对未知代码的完整高强度沙箱。Alpha 只运行天问仓库中经过人工审阅的五个任务。未来接入任意第三方任务前，需要单独做容器逃逸面、镜像来源和资源耗尽审计。

## 8. 版本与任务数据如何演进

### Alpha-A

- 五个任务全部是公开开发任务；
- 最终验证器不在模型工作区、不能被模型修改，但验收目标对模型公开；
- 每个任务先做“原始基线必须失败”和“参考解法必须通过”的作者校验；
- 每个任务先运行一次，建立能力基线，不做统计性结论。

### Alpha-B

- 继续使用其中一部分任务验证比较器；
- 每个版本从相同基线单独开始；
- 增加成对重复试验；
- 不在比较期间修改协议。

### Alpha-C

- 从真实问题中选一个明确、重复且可归因的触发问题；
- 先区分一次性问题、能力发现、用户偏好和真正可复用的 LearningSignal；
- 另设开发变体，避免只复制触发样例；
- 原因不明时允许有界 Experimental Run，实验改善不等于候选晋升；
- 候选只修改 `repo_task` Skill。

### Alpha-D

- 加入未参与学习的保护变体；
- evaluator 只返回必要汇总和失败类别；
- 晋升后运行不同后续任务；
- 逐步替换当前只检查 Skill 文本的 sealed evaluator。

## 9. 进度展示

用户看到的是证据化进度，不是模型私有思维过程。Alpha 至少显示：

- 当前 Goal、任务、轮次和阶段；
- 已确认的仓库基线与任务版本；
- 当前 Champion、完整模型标识和预算；
- 正在读取、修改或运行哪个已登记检查；
- 已验证事实、失败检查和剩余未知；
- Token、工具调用、动作和时间消耗；
- 当前是否等待用户审批；
- 最终差异摘要、独立验证结果和结论边界。

正常的低风险步骤不中断用户。只有目标、授权、重大风险或结果主观验收确实需要人判断时才询问。

## 10. 每阶段的停止条件

### Alpha-A 完成门

- 五个任务都能从登记基线创建一次性工作区；
- 每个任务的空白基线失败、参考解法通过；
- 五次真实模型试验都产生可审计的终态结果；
- 至少一项任务通过独立最终验证；
- Provider 凭据没有进入任务子进程；
- 没有工作区外写入、验证器篡改或容器边界违规；
- 结果报告明确成功数、失败数和失败位置，不作泛化宣传。

若执行设施完整但模型任务通过率低，先把原因分到模型、上下文、Skill、工具或任务难度；不能把低分自动解释成“需要学习”。

### Alpha-B 完成门

- 同条件约束有机器可核对的摘要；
- Champion / Challenger 工作区与上下文隔离；
- 成对结果可重复汇总；
- 比较器不会把缺失结果当零分或胜利。

### Alpha-C 完成门

- Observed Gap 能被分诊为普通修正、偏好绑定、继续观察或 LearningSignal；
- 候选来自真实 Case 和明确归因；
- 没有证据时能正常返回“无候选”；
- 原因不明时能在固定预算和停止条件下实验并保存新 Evidence；
- 候选修改范围最小且仍需外部比较。

### Alpha-D 完成门

- 保护任务未参与候选生成；
- 硬门通过且总体质量不倒退；
- 人工晋升和回滚均可审计；
- 不同后续任务提供了有限迁移证据。

## 11. 明确不做

Alpha 首轮不做：

- 直接 Fork Hermes；
- 直接接入完整 SWE-bench、Terminal-Bench 或 Harbor；
- 插件市场、通用任务注册中心或动态 Provider 路由；
- 多 Agent 并行、后台守护进程或分布式队列；
- 任意第三方依赖安装和开放网络代码执行；
- 自动修改 Goal、Action Gateway、安全门、评测协议或发布器；
- 模型微调、权重更新或强化学习；
- Web UI、任务面板或长期服务。

这些能力以后只在真实瓶颈出现时引入。

## 12. 与天问总体愿景的关系

五个代码任务只是第一个可控实验环境，不是天问的产品边界。天问的核心仍然是同一套持续学习过程：

```text
目标
→ 探索本地上下文与必要外部知识
→ 规划有限任务和子目标
→ 执行
→ 独立验证
→ 记录有前提、范围和代价的知识
→ 形成并比较改进候选
→ 人工治理下进化
→ 新问题再次进入循环
```

以后目标可以是完善天问、完成用户项目、改良工作流或学习其他领域。变化的是 Goal、工具和验证器，不是持续学习的基本协议。
