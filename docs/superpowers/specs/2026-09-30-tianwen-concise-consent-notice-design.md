# 产品同意通知的简明表达

## 已有问题与范围

上一轮一次性原生状态验证已保留九点产品通知，见 `docs/operations/tianwen-quarantine-status-live-20260930.md`。通知来自 `TianwenLearningConsentAgentService.runGuardedNoticeTurn` 的独立原生回合；当前提示要求解释完整告知，但未要求简短或限定表达形式。源码可确认这个提示缺口，不能仅凭它认定模型总会冗长或修复后必然简明。

本项在用户持续推进且不反复询问的既有授权内处理这一已记录的体验问题。仅修改产品通知自己的表达提示，不修改普通用户回答、告知条款、同意策略版本、授权记录、调度次数、账本或研究门槛；不重新升级刚交付的 Daily。

## 选项与决定

1. 在现有通知回合增加局部简短表达要求：复用原生 Agent、完整告知和工具禁用，改动最小；效果仍依赖模型。
2. 取消首次通知：减少消息，但失去现有知情告知，超出范围。
3. 改为固定多语言消息：输出长度确定，但需新建翻译与维护路径，并改变现有原生通知机制。

采用选项 1。给 v3 产品通知加一小段、无标题和编号清单的概括要求，保留发送给模型的数据范围、只读／当前与未来任务边界、同意范围和可关闭说明；不逐条复述或叙述内部通知回合生命周期。完整告知文本仍原样进入原生消息，首次 enable 返回的完整 disclosure 不变，历史 v1/v2 恢复通知不变。

## 验证与停止

缺少局部简短提示已由当前源码和保留的原生通知核对，不重跑旧模型答案。此次是局部提示文案修改，不添加只重复新文案字面的测试。复用真正调用原生 Agent 的既有通知回归，核对完整告知仍在、工具不能执行、同意未开启、重复观察只投递一次；运行整个 consent-agent 文件及八包类型检查。

工程通过只证明正确投递指令与保留边界，不证明真实模型已改好表达。不开新状态问答、不重问旧问题；以后真实任务自然产生首份通知时再观察表达，不将此作为自动学习发布新门槛。若工程回归失败，先保留失败并定位，不通过移除告知或放开工具来取绿。
