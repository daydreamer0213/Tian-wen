# Tianwen v0.1 Controlled Real Activity-04 Design

**Status:** approved design

**Date:** 2026-08-25

**Operation baseline:** `main@a85561a2698883099d27cc7a1559882317b1db5e`

**Operation CI:** run `32804515972`, `push`, attempt 1, all three jobs successful

## 1. Product goal

Activity-04 is the first formal real-Provider lifecycle attempted after the ordinary installed
one-shot Profile path was repaired and proved end to end.

The product flow under test is:

```text
verified installed product
→ activate deepseek-official/deepseek-v4-pro
→ fresh status confirms the selection
→ invoke controlled-lifecycle exactly once
→ let the existing DSH/Tianwen lifecycle reach one terminal result
→ restore offline selection
→ fresh status confirms offline
```

The core question is whether the installed product can now complete its real Agent, tool, Session,
Evidence, Outcome, evaluation, Shadow and pointer-transition path. Receipt formatting, path
inventories and additional forensic machinery are not the product goal.

## 2. Why this is a new Activity

Activity-01 stopped at CLI usage before lifecycle. Activity-02 reached the controlled runner but
stopped in the seed stage. Activity-03 never invoked `controlled-lifecycle` because its model
activation process ended abnormally. Those results remain immutable.

Since then, two product defects have been repaired and merged:

1. controlled seed integrity now requires exact tool inputs, persisted Session readback, complete
   decision/verifier/Evidence validation and parent Skill-use proof before governance writes;
2. the ordinary one-shot Profile lifecycle now settles HMR watcher readiness, completes shutdown
   and exits normally.

The fresh R2 installed proof on the operation baseline then completed all four zero-request model
commands with exit 0 and empty stderr:

```text
model use --model deepseek-v4-pro
model status
model use --model offline
model status
```

Every receipt reported `modelRequestsDelta=0`; final selection was
`tianwen-offline/phase2-smoke`; Sessions remained absent and Evolution remained empty. This closes
the setup and process-lifecycle prerequisites. It does not claim that a real Provider lifecycle has
passed.

## 3. Product-first decisions

### 3.1 Reuse the verified R2 installation

Activity-04 reuses the R2 installed product at:

```text
D:\DevData\tianwen-one-shot-profile-lifecycle-proof-r2-product
```

The installation is the exact operation-baseline product, its archive digest is
`sha256:a5963e41777959ba9250067f9ec43ec69e81f9f8f4bdcc7e76ece4ace3722230`, and its
post-proof state is offline with no Session or Evolution files.

Running another identical installer would add roughly 35 minutes and another installation failure
surface without testing a different product behavior. Freshness needed for attribution belongs to
the operation state, workspaces and Sessions, not to repeating an already-proved installation.

Before formal execution, read-only checks must confirm the R2 receipt, archive identity, canonical
launcher, final offline receipt and empty Session/Evolution state still match. Any drift stops the
operation; the installed product is never patched or repaired in place.

The R2 proof used a dummy credential and loopback Provider URL only in those zero-request child
environments. Activity-04 must instead inherit the operator's configured `DEEPSEEK_API_KEY` reference
without reading its value and must not set `DEEPSEEK_BASE_URL` or another test endpoint override.
The real Provider route is part of the product path being tested.

### 3.2 Create fresh execution identity

Activity-04 creates only new formal state:

```text
operationRoot = D:\DevData\tianwen-one-shot-profile-lifecycle-proof-r2-product\controlled-operation\activity-04
evidenceRoot = D:\DevData\tianwen-controlled-real-activity-04-evidence
activityLabel = tianwen-v0.1-controlled-real-activity-04
```

The operation uses 20 new non-nested workspaces and 25 new Session IDs, all containing the
`activity-04` namespace. No Activity-01/02/03 operation, Session, ledger or evidence artifact is
read or reused.

### 3.3 Keep one owner for every lifecycle

DSH remains the only owner of Agent creation, model turns, tools, Session persistence and Profile
shutdown. Existing Tianwen Runtime and Evolution services remain the only owners of governed Run,
Outcome, Skill-use, evaluation and pointer facts. Activity-04 adds no controller, retry loop,
transaction framework, checker, postmortem processor or telemetry system.

## 5. Activity consumption and command state machine

Model activation is product setup. It sends no formal Agent work and does not consume Activity-04.
The first direct official `controlled-lifecycle` invocation consumes Activity-04.

The exact state machine is:

```text
offline-ready
  → model-use-deepseek
  → deepseek-confirmed
  → controlled-lifecycle (Activity-04 consumed here)
  → passed | stopped | transport-failed
  → model-use-offline
  → offline-confirmed
```

Rules:

1. Activation and confirming status each run at most once in this released attempt.
2. If either setup command fails, preserve the scene, restore offline once where safe, and stop.
   Activity-04 remains unconsumed because lifecycle never began.
3. `controlled-lifecycle` runs exactly once. Its first terminal result is permanent.
4. Offline restoration and final status each run once after every lifecycle terminal result.
5. No command is retried, no missing arm or Session is supplemented, and no result is selected away.

## 6. Product-native readiness

Before the lifecycle creates the first Agent, existing product preflight must prove:

- the reviewed manifest and installed archive digest;
- settled installed loader/services;
- exact DeepSeek selection and configured credential reference;
- absence of a test or loopback Provider endpoint override;
- retry `normal/0` and the fixed tool surface;
- empty Evolution, ledger, Champion and controlled pointer;
- no persisted or live Session/Agent;
- 20 frozen workspaces and the exact parent B Skill;
- 25 fresh Session identities.

The operation does not add a second readiness checker. A small one-use generator may materialize the
reviewed manifest and workspace files, using the existing production manifest parser and evidence
digest seam. It is an operation artifact, not product code or a general task language.

## 7. Functional success

Success is one valid `tianwen.controlled-real-skill-lifecycle.v1` `passed` receipt plus:

- 25/25 formal roles closed: 2 seed, 10 B/C, 5 evaluator, 5 Shadow and 3 transition;
- D1 is `not-met` and produces one Ticket;
- D2 is `met` counterevidence;
- controlled evaluation passes;
- all isolated Shadow tasks pass;
- Promote, Rollback and Restore are verified;
- pointer sequence is `B@rev1 → C@rev2 → B@rev3 → C@rev4`;
- final official model status confirms offline with `modelRequestsDelta=0`.

The operation is also functionally complete when it returns one valid `stopped` receipt and then
restores offline. That is a failed product result, not a reason to replay the Activity.

## 8. Evidence boundary

Use only what is needed to decide the product result:

- `receipt-certified`: fields from valid official model or lifecycle receipts;
- `durable-observed`: already-persisted Session and Evolution facts read without mutation;
- `filesystem-observed`: finite identity and digest checks required for the operation substrate;
- `unknown`: anything without a valid product receipt or independent fact source.

Provider-account request count and actual tool-body execution count remain `unknown` unless an
existing independent source proves them. Session events are not promoted into billing facts. Raw
prompts, model output, tool arguments/results, evaluator reasoning, Skill content, Session/Run/
Candidate IDs, credentials, private paths and raw errors are not copied into public reporting.

There is no checker or postmortem run. Terminal inspection is limited to the official receipt and
ordinary read-only product state needed to explain which product stage closed.

## 9. Failure behavior

If readiness or activation fails before lifecycle, preserve the new operation/evidence scene and
stop without claiming Activity consumption.

After lifecycle begins, preserve its unique result. A `stopped` receipt, nonzero exit, malformed
transport or missing receipt is terminal for Activity-04. Do not change code, task material or
configuration and then rerun against the same authority. Offline recovery remains a separate
zero-request product action and does not erase the result.

## 10. Implementation and release boundary

No `packages/**`, workflow, installer, CLI, Profile, dependency or lockfile change is planned.
The repository work is limited to this design, a concise implementation/operation plan and one
Activity-04 packet that binds fresh identities to existing task authorities.

Those documents form one reviewed feature. The feature must enter `main` through a normal controlled
merge, and the matching automatic exact-main `push` attempt 1 must have Python, TypeScript and
installer-windows all successful before generator or product execution.

The real Provider operation may then execute once under the standing project direction. It must not
start from an unreviewed branch or use Activity-03 artifacts as live input.

## 11. Explicit non-goals

- no new task, answer tuning, sixth evaluation or additional Shadow run;
- no new Agent loop, workflow engine, scheduler, database, transaction or rollback framework;
- no extra installer proof when the R2 installation remains exact and empty;
- no retry, model/token/CNY cap, price polling or cost-estimation subsystem;
- no checker, postmortem, probe, smoke, dry-run or Goal;
- no change to Activity-01/02/03 history;
- no claim of natural-user or external-user improvement.
