# DEV 功能检查宿主固定配置

## 已证实问题与职责

实际 DEV 驱动逐轮把 isolated.workRoot 指向本轮运行目录。原执行器摘要包含完整配置，普通 checkerDigest 又包含执行器摘要；原来源配对还要求 requiredCondition 完全相等。故即便同一语言、镜像、检查代码和原必需条件，仅更换回执目录也会割裂跨轮来源身份。省略 timeoutMs 与显式 20000 同样不同。这是宿主配置问题，不是精确来源分组规则错误。

选择复用现有工厂并固定宿主配置：版本控制的 JSON 配置保存当前 D: Docker 路径、端点、已缓存官方固定镜像、明确 20000ms、各语言的持久回执目录。后续不同任务读取原配置并封存其摘要，运行轮次摘要另存各自小目录。配置不含任务题目、期望或 requiredCondition；原任务必需条件仍独立事前声明，仅确实相同才按原分组。

不选择修改生产 identity/忽略目录摘要：会改变原分组语义及环境绑定，当前无需。也不选择重新建宿主/Agent 循环：现有公开工厂和运行链已支持。仅配置，禁止新开自动启用开关、重评历史或拼接不同条件。

## 文件与边界

`scripts/development-isolated-node-host.json` 只提供当前 DEV 的 JavaScript/可擦除类型 TypeScript 两份配置。`scripts/development-isolated-node-check.mjs` 是实际公开工厂的薄转发：从目标扩展名选择原固定配置，拒绝调用者传 isolated 覆盖，原请求/案例/条件等交回原工厂验证；后续原生驱动导入此入口，事前同时封存转发文件和 JSON 摘要。不是通用安装器，不启动 Docker、不下载镜像、不执行候选、不挂载正式宿主。持久根位于 `D:/DevData/tianwen-development-learning-20261001/functional-checks/`；不拷贝 profile/依赖。原 unknown-cleanup 检查和完整隔离保留。不能删除正在使用的合同/回执或未知清理标记来强行继续。

与本轮 receipt-summary 的冻结运行彻底分开：原任务已终态，原配置/结果/双审/账本保持。新配置只用于后续任务，不恢复或追认旧来源资格。代码、镜像、条件变化仍按原规则改变身份；固定目录不承诺永久相容。

## 最便宜的反证和验收

在当前实际发行根使用公开普通 Node 工厂，仅 prepare 两个请求/不同案例：同一 JSON 配置和相同原条件，其 checker 身份相同、各自 contractDigest 不同。改变 requiredCondition 仍应不同；改变 workRoot 仍应不同；JS/TS 仍应不同。准备真实固定缓存 Docker 镜像，不调用模型/执行候选、不新增任务/研究/反馈或修改正式账本。保留旧每轮配置导致不同身份的对照，不改生产代码掩盖它。

再由标准 Node 消费薄入口并做两次实际 prepare，验证相同配置/条件的身份、独立合同与拒绝 isolated 覆盖；薄入口缺失的首红保留。核对原 84 容器 ID 无变化、准备不产生执行回执、持久目录无未知清理、Docker 恢复停止、D≥15GiB。本项只证明后续宿主可以稳定保留检查身份，不证明未来真实任务已启用此入口、自然重复失败、来源独立、研究采用、开放语义安全或未来收益。main/Daily NO-GO、原隔离/同意/门槛/十工作日窗口保持。
