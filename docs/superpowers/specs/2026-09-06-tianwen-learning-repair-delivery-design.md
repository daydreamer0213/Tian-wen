# Versioned local delivery of the reviewed learning repairs

## Inherited decision and current evidence

The total-route plan already authorizes reviewed local delivery after exact-main
CI and user-data preservation. The existing installer intentionally treats a valid
current-version receipt as immutable. Current daily Runtime is `0.1.12`, Desktop
is `0.1.0-preview.13`, and DSH is `0.1.1-rc.2`. None is this branch's new release.
Overwriting the same-version archive or deleting receipts is not an upgrade path.

Reuse the established patch-release path with Runtime `0.1.13` and Desktop
`0.1.0-preview.14`. This is packaging/compatibility preparation, not a claim that
the genuine learning efficacy route is complete. The user delegated these ordinary
delivery details; no new external publication or trust boundary is introduced.

## Bounded design

Update existing current-version metadata, archive arguments and directly affected
tests. Add exactly `0.1.12` to the existing same-DSH predecessor recognition,
retaining `0.1.11`, `0.1.10` and the old independently frozen rc.7 migrations.
Preserve archive hashes, complete Profile matching, receipt/path checks, rollback,
selected DSH home/store, idempotence and unknown-version refusal. DSH and all
dependencies stay unchanged. No migration framework or new persistent state.

The controller compared the current `renderProfilePatch` body to the already
frozen `renderRuntime011PredecessorProfilePatch`: both are exactly 860 characters
and byte-equivalent in the checked source. Thus `0.1.11` and `0.1.12` can use the
same independently frozen learning-loop predecessor renderer, with a descriptive
name/comment. Do not derive old bytes from the evolving current renderer or add
another verbatim copy. Keep the distinct `0.1.10` no-learning-loop renderer.
Version-specific archive/receipt matching remains exact even when patch bytes
are shared. Tests use independent historical fixtures, not production renderers.

The alternatives are leaving safe fixes undelivered, or mutating a same-version
installation. The former does not finish the authorized engineering delivery;
the latter defeats immutable release checks. An ordinary next patch version is
the existing narrow solution. No new updater abstraction is needed.
