# Source-only answer review v9 design

## Problem and scope

The v8 first-pass product review correctly handled five frozen pending/failure and advice cases, but a newly generated ordinary answer exposed a broader source-boundary problem. In a request to summarize only supplied records, its answer changed a total of twelve items into "completed twelve checks", stated how future arrangements *will* be decided without a supplied decision process, then said it made no additional inference. A separate first-pass diagnostic gave the unchanged answer two `met` reviews; a one-phrase control split `met` / `not-met`, with the latter correctly identifying the future-process and self-certification issues. The total/completion phrase is ambiguous, so the design does not encode that specific wording as a guaranteed error. The whole result remains diagnostic, not a regrade of the ordinary task.

Implement a versioned v9 quality contract and native reviewer instruction for three general distinctions: (1) a source total does not by itself establish that every counted check, task or outcome was completed; distinguish completion of an inspection from completion of the underlying item only when the source establishes that distinction; (2) a declarative future plan, deciding procedure or commitment attributed to an external actor needs source authority, even when it is a plausible consequence of open items; a clearly optional recommendation or explicitly fallible, task-compatible inference remains permitted when the user's instructions allow it; (3) an answer's own assurance that it contains no extrapolation or uses only records must be checked against the entire answer, rather than automatically treated as harmless courtesy. An unsupported or contradictory assurance cannot upgrade an unsupported claim.

This changes review judgment only. It does not change task admission, consent, answer generation, feedback attribution, research selection, method activation, verdict consensus or native proof format. Keep the claim audit v2 shape and two blind independent native reviewers. No keyword-based host rejection, extra reviewer, retries or reinterpretation of stored evidence.

## Versioning and compatibility

Freeze the exact current v8 contract and instruction as legacy. Generate v9 only for new tasks. Parse v1–v9 exactly; altered criteria remain invalid. Route v6/v7/v8/v9 each to its corresponding instruction. An audited v9 task or study arm must retain the same two-review requirements as v8, and mixed contract versions cannot form compatible study support. Previously saved v8 tasks, audits and proofs remain readable without changed text.

## Verification and stop conditions

First prove current-v9/legacy-v8 parsing, native instruction routing, task and study replay, and versioned dual-review guards with focused tests and direct TypeScript checking. Then freeze an isolated candidate runtime, novel source/answer pairs, expected decisions, model configuration and one-shot stop rules before a provider call. Use new cases for an unsupported completion-total claim, an unsourced declarative future procedure, a false self-assurance, an accurate total/completed breakdown and a clearly optional recommendation. Inspect both native audits and exact source quotes. Any unsafe `met`, normal advice rejection, invalid proof, or changed legacy behavior stops the candidate. This direct reviewer test cannot establish ordinary answer quality, consented task admission, feedback, research, activation, later-task effect or production readiness. main/Daily remains NO-GO.
