# Captured file facts for ordinary local-file tasks

E043 and E044 showed the same product boundary: the model completed native file reads, then naturally used PowerShell to count lines or compute hashes. Those commands ran, but the conversation file observer could not certify their dynamic pipelines, so the final file evidence failed closed and no original-result reviewer ran. E049 separately showed that an unexpected `write` in a chat-output task must also remain ineligible. E048 proves two native reviewers can complete a controlled read-only task; it does not solve these ordinary queries.

## Decision

Add one narrow Tianwen-owned native tool for **facts about UTF-8 files captured for the current `local-files` task**: canonical workspace-relative path, byte length, SHA-256 of exact captured bytes, and a precisely defined line count matching the native read line-number convention. The tool must compute its value from the same complete preimage stored as `task-file-input-captured`, rather than independently reading a possibly changed file after the capture. If no preimage exists yet, it may make a first capture through the existing safe `conversationFilePath` / `readConversationFile` path and record it before returning the value. This keeps the order of `read` and the new tool irrelevant to eligibility while retaining the current 8-file / 96-KiB-per-file / 128-KiB-total bounds.

The tool is available only to a root ordinary task in the current workspace; it does not accept absolute paths, links, external files, arbitrary commands, recursive scans, generated outputs, or a user-supplied hash algorithm. A missing, oversized, non-UTF-8, changed or unsafe file must produce no certified fact. Reusing the captured content must not let a later mutation pass: the existing terminal snapshot comparison stays mandatory for chat-output tasks.

Persist a bounded fact record tied to the native call/result identity, task/session, canonical path, captured preimage digest and exact tool result. On recovery, recompute every fact from the persisted frozen preimage and compare the full result; never trust a model-authored statement or a printed PowerShell result as the fact. Supply only these recomputed facts as `tool` source items to the two reviewers. Keep file contents as their own initial-file source items, and do not treat a count or hash as proof of any broader interpretation of the file. Preserve historical ledger schemas when no fact query occurred.

The existing `Get-Location` / `Get-ChildItem` directory receipt remains the directory-navigation channel. Arbitrary `pwsh`, including E044's `ForEach-Object` pipelines, retains `material-unavailable`; `write` in chat-output mode retains `unsupported-tool`. The new tool should be described in the ordinary model's tool list as the supported way to ask for captured file facts. Do not make an acceptance-only prompt that forbids natural tool choice.

## Implementation sequence and gates

1. Freeze the native tool's output shape and line-count semantics. Test UTF-8 BOM, CRLF/LF, trailing newline, empty file, Unicode, and byte-accurate SHA-256. Start with a test showing that a real observed count/hash query currently yields no eligible evidence.
2. Bind execution to the existing safe preimage capture and native tool call/result. Test before-`read` and after-`read`, repeated calls, file changes, links, workspace escape, missing and oversized files, and a forged or mismatched result. Recovery must recheck the same frozen bytes without reopening the workspace file.
3. Add the narrowly typed derived facts to reviewer evidence, preserving source roles and every old no-fact material digest. A simulated complete task should reach two reviews; an arbitrary PowerShell pipeline and a chat-mode write should still stop before review.
4. Freeze an exact candidate and run a **new unrestricted ordinary desktop task** that actually needs directory listing, line counts and hashes. Audit native sessions, captured bytes, terminal file state, both reviewers, consent and study state. A model choosing unsupported shell syntax remains a failure to solve, even if it happens to give the right answer. Keep main/Daily NO-GO until this chain and its result quality pass.

Extending the existing directory-command PowerShell parser to accept general scriptblocks is rejected: its current receipt proves a deliberately literal four-command subset, while `Get-Content`, `Measure-Object`, `Get-FileHash` inside `ForEach-Object` can read dynamic paths and produce facts that the current ancillary projection does not bind to frozen file content. A standalone facts tool gives a smaller, reviewable authority boundary.
