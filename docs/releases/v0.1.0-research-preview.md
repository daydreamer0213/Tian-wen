# Tianwen v0.1.0 Research Preview

**Status:** public prerelease exists; this repository source reflects the
completed Stage 7 facts. Updating the already-published GitHub prerelease text
is a separate external action.

**Updated:** 2026-08-22

## Problem

An Agent can complete one session without answering the longer-lived
governance questions: what evidence supports the result, whether a problem is
repeated and attributable, and whether a future change has been independently
shown to be better. Tianwen explores a learning control plane for those
questions without replacing the Agent that performs the current task.

This is deliberately a research preview. It publishes a bounded, auditable
execution-and-learning-governance result and its limits; it does not claim
general autonomous learning, production maturity, or external-user adoption.

## One Runtime and one learning control plane

DSH 0.1.0-rc.7 is the only product Agent Runtime. It owns the current Agent
loop, models and providers, tools and MCP, sandbox, Session and Session Query,
Skill, Jobs, Workflow, Subagent, Message Feedback, Approval, and permissions.

Tianwen is the non-interfering learning control plane around that Runtime. Its
product boundary covers cross-run Goal Graph, Evidence provenance, learning
attribution, and future-run version governance. DSH Message Feedback may be an
attribution input; it is not a Lesson by itself. A DSH Job is process-local
work; it is not a durable cross-run Learning Ticket.

Alpha remains an experiment and evaluation lab, not a second product Runtime.
The historical Python `RepoTaskRuntime` / `AlphaRuntime`, Dynamic, Artifact,
and global Champion paths are not product activation or routing paths. See the
[architecture overview](../tianwen-architecture-overview-v2.md) for the current
ownership boundary.

## Evidence this preview now carries

### Scripted mechanism proof

The zero-cost fixtures prove normal DSH Agent execution, read-only Evidence
projection, no-case behavior, explicit-feedback and repeated-Outcome intake,
one deterministic synthetic Case/Lesson/recorded Candidate path, and one
paired Evaluation record. The paired result is deliberately `INCONCLUSIVE`,
`not-comparable`, and `needs-evidence`; it never claims Candidate C is better.

These fixtures use no network, configured Provider, paid model, user data, or
production incumbent. They prove mechanisms only.

### Project-owner natural product evidence

Stage 7 completed one fresh, useful natural task through the installed DSH
rc.7 product path with a configured model and real tools. The formal attempt
ran once and produced:

- Goal complete;
- 45 of 45 Evidence records complete;
- `Outcome=met`;
- learning=`no-case`;
- parent Skill-use=`recorded`;
- model restored to offline after the run.

No failure was manufactured and no result was selected from retries. Because
the task produced no qualifying learning problem, it correctly created no
Ticket, Case, Lesson, Candidate, Evaluation, Shadow, or Promotion. This is
valid single-user project evidence from the project owner; it is not external-
user validation or proof of broad efficacy.

### Installed-product operational evidence

The final official offline installer returned one canonical ready receipt. All
16 published Profile files were regular files with independent identity and no
source hardlinks. Sessions and Evolution data were unchanged. The installed
CLI's read-only status command returned exit 0 for a successfully completed
Goal without exposing governed private-ledger facts.

The operational sequence, including earlier stopped attempts, remains in the
[Stage 7 handoff](../operations/tianwen-stage7-natural-run-evidence-trial-handoff.md)
and the [installer migration handoff](../operations/tianwen-rc6-rc7-managed-install-migration-handoff.md).

## Reproduce the zero-cost mechanisms

Install the frozen dependencies and run:

```console
pnpm install --frozen-lockfile
pnpm demo:research-preview
pnpm demo:explicit-correction
pnpm demo:repeated-outcome
pnpm demo:governed-skill-candidate
pnpm demo:paired-skill-evaluation
```

These commands reproduce scripted mechanisms, not the configured-model natural
task and not a claim of Candidate improvement.

## Known limitations

- The recorded Candidate and paired Evaluation are synthetic mechanism proof.
  No naturally triggered product Candidate has passed real paired B/C yet.
- The remaining bounded development-closeout lifecycle is a frozen five-task
  real B/C with blind controlled evaluation, isolated Shadow, project-owner-
  approved Promotion, and a Rollback rehearsal.
- There is no production SLA or finished user interface.
- There is no external-user validation or multi-user generalization evidence.
- One successful task should not automatically create learning, and no future
  version may hot-swap a currently running Agent.

## Bounded closeout route

The current route is:

```text
v0.1 documentation closeout
→ frozen five-task paired B/C through the real Runtime
→ independent blind evaluator-Agent scoring
→ isolated Shadow
→ explicit project-owner Promotion approval
→ bounded Rollback rehearsal
→ development closeout
```

The evaluator-Agent evidence is controlled/simulated and will be labelled as
such. External-user feedback is a future generalization check, not a blocker
for completing this single-user research project. Full entry and exit gates are
in the [v0.1 closeout design](../superpowers/specs/2026-08-22-tianwen-v0.1-closeout-and-controlled-evaluation-design.md).
